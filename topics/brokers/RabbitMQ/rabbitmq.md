# RabbitMQ

**RabbitMQ** — брокер сообщений: посредник, который принимает сообщения от приложений, маршрутизирует их в
очереди и доставляет потребителям.

<a id="summary"></a>

## [Summary](#содержание)

**RabbitMQ — брокер сообщений**, который принимает сообщения от отправителей, маршрутизирует их и доставляет
потребителям. Он позволяет приложениям взаимодействовать асинхронно: отправителю не обязательно ждать
обработки, а получателю — работать в момент публикации. Ниже — краткая модель для AMQP 0-9-1 и обычных
очередей.

Основной способ доставки — **push**: consumer регистрирует подписку на очередь, после чего брокер сам
отправляет ему сообщения. Просто открыть соединение недостаточно. Также есть получение по запросу —
`basic.get`.

Приложение обычно держит долгоживущее **connection**, внутри которого открывает **channels** — логические
каналы для команд и доставки по одному TCP-соединению. Через channel Go-приложение может объявить exchanges,
очереди и bindings, публиковать сообщения и запускать consumers. Сущности создаются на стороне RabbitMQ.

Закрытие connection закрывает все его channels; обычная очередь не принадлежит объявившему её channel.

Основной путь сообщения:

```text
Publisher → Exchange ── по правилам bindings ──→ Queue → Consumer
```

**Publisher** публикует сообщение в **exchange**, указывая **routing key**. Exchange выбирает очереди по
своему типу и **bindings** — связям с очередями и параметрам маршрутизации. **Queue** хранит сообщения до
обработки с учётом настроек и ограничений. **Consumer** получает сообщения из очереди.

Exchange не хранит историю для будущих очередей.

Основные типы exchanges: **fanout** направляет сообщение во все привязанные очереди; **direct** сравнивает
ключи точно; **topic** сопоставляет routing key с шаблоном (`*` — одна часть, `#` — ноль или больше);
**headers** использует заголовки. Если подходят несколько очередей, каждая получает независимую копию.

Если обычных consumers несколько у одной очереди, они делят работу: конкретная доставка назначается одному из
них. Это разные уровни распределения.

В режиме **manual ack** доставленное сообщение остаётся неподтверждённым (`unacked`). После обработки consumer
отправляет **ack**, и брокер может удалить сообщение из этой очереди. **Nack с requeue=true** возвращает
сообщение для повторной доставки, не обязательно в конец очереди.

**Requeue=false** направляет его в настроенный **DLX**, иначе сообщение отбрасывается. При потере channel или
connection неподтверждённые доставки возвращаются для повторной выдачи после обнаружения закрытия брокером.
**Prefetch** ограничивает количество неподтверждённых доставок.

**Publisher confirms** — отдельные подтверждения от брокера отправителю. Они подтверждают публикацию, а не
бизнес-обработку consumer. Для обнаружения публикации без подходящей очереди используют **mandatory** и
обработку возвратов.

RabbitMQ использует **и RAM, и диск**: конкретное размещение зависит от типа очереди и реализации хранения.
**Durable** относится к сохранению очереди после перезапуска; **persistent** — к устойчивому хранению
сообщения. Для classic queue базовое сочетание — durable-очередь, persistent-сообщения и ожидание publisher
confirms.

**Quorum queue** — durable-очередь с репликацией на основе Raft. Ни одна из этих настроек не означает хранение
сообщения навсегда: после consumer ack обычная очередь перестаёт его выдавать.

Повторные доставки возможны, поэтому обработчик должен учитывать повторы и при необходимости быть
**идемпотентным**: повторная обработка события не должна повторять бизнес-эффект.

**TTL** ограничивает время жизни сообщения в очереди, а **DLX** позволяет перенаправлять сообщения при отказе
от обработки, истечении TTL и других настроенных условиях.

Отправителю не обязательно знать, какой экземпляр приложения обработает сообщение. Отправитель и получатель
могут работать в разное время: очередь хранит сообщения до доставки, с учётом её настроек и ограничений.

RabbitMQ поддерживает несколько протоколов. В этом конспекте рассматриваются **AMQP 0-9-1 и обычные очереди**.
У RabbitMQ Streams другая модель хранения и чтения.


**Кластер** объединяет несколько узлов RabbitMQ, общающихся по сети. У каждой quorum queue свой
leader и группа реплик; кластер сам направляет операции к лидеру. Копии Go-приложения могут
подключаться к разным узлам и читать одну очередь. При отказе узла выбор нового лидера и
переподключение приложения — разные механизмы: приложению нужны доступные альтернативные адреса.

## [Часть I. Теория](#содержание)

<a id="1-модель-и-основные-термины"></a>

### [1. Модель и основные термины](#содержание)

```text
Publisher → Exchange → Queue → Consumer
                │
                └── выбор очередей по bindings
```

| Термин | Значение |
| --- | --- |
| **Publisher / producer** | Приложение, публикующее сообщения |
| **Message** | Сообщение: тело с данными и метаданные |
| **Exchange** | Принимает публикации и маршрутизирует их в очереди |
| **Queue** | Хранит сообщения и выдаёт их потребителям |
| **Binding** | Связь exchange с очередью, содержащая параметры маршрутизации |
| **Routing key** | Ключ маршрутизации, который publisher задаёт при публикации |
| **Consumer** | Подписка на доставку из очереди; также так называют приложение-получатель |
| **Connection** | Сетевое соединение приложения с брокером |
| **Channel** | Логический канал внутри connection для операций AMQP 0-9-1 |
| **Virtual host, vhost** | Логически изолированное пространство очередей, exchanges, bindings и прав доступа |

Тело сообщения для брокера обычно является набором байтов. Например, приложение может передавать JSON, но
сериализация и интерпретация данных — ответственность приложений. В метаданных могут находиться
`content_type`, `message_id`, заголовки и другие свойства.

RabbitMQ называют «умным брокером», в частности, из-за маршрутизации на стороне брокера. Это не означает, что
он выполняет бизнес-логику consumer.

<a id="кто-создаёт-exchange-очередь-и-binding"></a>

#### [Кто создаёт exchange, очередь и binding](#содержание)

**Топология** — набор exchanges, очередей и bindings, определяющий маршруты сообщений.

Go-приложение может объявлять и настраивать топологию через AMQP-клиент. В `amqp091-go` для этого открывают
`*amqp.Channel` из `*amqp.Connection` и вызывают `ExchangeDeclare`, `QueueDeclare`, `QueueBind`. Команды
выполняет брокер: сущности создаются на стороне RabbitMQ и доступны другим приложениям с нужными правами в том
же vhost.

Таким образом, приложение **управляет созданием**, а RabbitMQ **хранит сущности и исполняет маршрутизацию**.
Открытие connection само по себе не создаёт пользовательскую топологию. Её также можно подготовить средствами
администрирования или инфраструктурной конфигурацией.

Объявить топологию может publisher, consumer или отдельный процесс подготовки — обязательной привязки к одной
роли нет. Созданная очередь не принадлежит объявившему её channel; особенности владения exclusive-очередью
задаются отдельно и относятся к connection.

Повторное объявление с совпадающими параметрами обычно допустимо. Несовместимое объявление существующей
сущности, например изменение `durable` очереди, приводит к ошибке channel. Это не способ изменить её
настройки.

Binding связывает exchange с очередью, а подписка consumer связывает получение из очереди с клиентом. Создание
binding не запускает consumer.

<a id="2-соединения-и-каналы"></a>

### [2. Соединения и каналы](#содержание)

**Connection** — долгоживущее сетевое соединение приложения с RabbitMQ. Обычно это одно TCP-соединение, при
необходимости защищённое TLS. На этапе подключения выполняются согласование параметров, аутентификация и выбор
vhost.

**Channel** — логический двунаправленный поток AMQP-операций внутри connection. Каналы позволяют использовать
одно сетевое соединение для нескольких независимых контекстов работы.

<a id="как-несколько-channels-используют-одно-соединение"></a>

#### [Как несколько channels используют одно соединение](#содержание)

```text
Go-приложение                 один TCP connection                 RabbitMQ
┌───────────────┐                                            ┌───────────────┐
│ Channel 1     │──┐                                      ┌──│ Channel 1     │
│ Channel 2     │──┼── кадры с номерами каналов ⇄ сеть ⇄ ───┼──│ Channel 2     │
│ Channel 3     │──┘                                      └──│ Channel 3     │
└───────────────┘                                            └───────────────┘
```

Данные AMQP передаются кадрами. Номер channel позволяет клиенту и брокеру направлять кадры в нужный логический
контекст. Это **мультиплексирование**: несколько потоков операций разделяют один транспорт. Channels не
создают отдельные TCP-сокеты и не дают отдельную полосу пропускания.

Channel не является очередью или участком хранения сообщений. В нём учитываются операции и состояние
взаимодействия: подписки, неподтверждённые доставки, режим confirms и другие параметры.

<a id="связь-channel-с-сущностями-брокера"></a>

#### [Связь channel с сущностями брокера](#содержание)

```text
Клиент A                                          RabbitMQ, один vhost
Connection A
├── Channel 1 ── ExchangeDeclare / QueueDeclare ──→ Exchange / Queue
│             └─ QueueBind ─────────────────────→ Binding
├── Channel 2 ── Publish ────────────────────────→ Exchange → Queue
└── Channel 3 ←─ доставка из Queue ────────────── Queue
              └─ ack ─────────────────────────→ брокер

Клиент B
Connection B
└── Channel 1 ── Publish / Consume ──────────────→ те же сущности
```

Exchange и queue не привязаны к одному channel. Разные channels и connections могут обращаться к одной
сущности при наличии прав. Номера каналов имеют смысл только внутри своего connection: Channel 1 клиента A и
Channel 1 клиента B — разные каналы.

<a id="что-разделяется-а-что-относится-к-channel"></a>

#### [Что разделяется, а что относится к channel](#содержание)

| Уровень | Что к нему относится |
| --- | --- |
| Connection | TCP-транспорт, аутентификация, выбранный vhost, heartbeat |
| Channel | Подписки consumer, delivery tags, режим publisher confirms; через него задают QoS |
| Vhost / брокер | Exchanges, очереди, bindings и содержимое очередей |

Delivery tags независимы между channels. На двух channels может одновременно существовать доставка с тегом
`1`; ack нужно отправлять через channel, получивший соответствующую доставку.

Один channel может публиковать в разные exchanges и обслуживать несколько подписок. Разделять channels по
ролям удобно, но протокол этого не требует. Channel AMQP и Go-тип `chan` — разные понятия: библиотека может
возвращать Go-канал с доставками, но это локальная структура приложения.

<a id="жизненный-цикл-и-ошибки"></a>

#### [Жизненный цикл и ошибки](#содержание)

```text
Открыть connection
  ├── открыть channel A → использовать → закрыть A
  └── открыть channel B → использовать дальше
Закрыть connection → закрываются все его channels
```

Connection и channels обычно переиспользуют: открытие каждого требует обмена с брокером. Channels дешевле
отдельных connections, но тоже расходуют ресурсы и имеют согласованный лимит количества.

Некоторые ошибки протокола закрывают только channel, например несовместимое объявление очереди. Другие
channels могут продолжить работу, если connection остаётся исправным. Потеря connection затрагивает все его
channels; приложение должно восстановить необходимые каналы и подписки.

После закрытия channel его consumer-подписки прекращаются. Неподтверждённые доставки в manual ack возвращаются
для повторной доставки после обнаружения закрытия брокером. Обычные очереди и exchanges от одного лишь
закрытия channel не исчезают; отдельно действуют правила auto-delete, exclusive и другие настройки жизненного
цикла.

<a id="channels-и-параллелизм-в-go"></a>

#### [Channels и параллелизм в Go](#содержание)

Несколько channels позволяют разделить работу, но используют общую сеть: задержки и ограничения одного
connection могут затронуть все его каналы. Поэтому для изоляции потоков публикации и потребления иногда
используют отдельные connections.

Удобная схема владения — отдельный channel для независимого publisher или consumer. Количество channels не
обязано совпадать с количеством goroutines: пул обработчиков может обслуживать одну подписку.

При совместном использовании нужно учитывать правила клиентской библиотеки, особенно подтверждения нескольких
доставок через `multiple=true`.

См. [устройство channels](https://www.rabbitmq.com/docs/channels) и [API
amqp091-go](https://pkg.go.dev/github.com/rabbitmq/amqp091-go).

<a id="3-маршрутизация-и-exchanges"></a>

### [3. Маршрутизация и exchanges](#содержание)

Publisher публикует сообщение **в exchange**, указывая его имя и routing key. Exchange выбирает очереди по
своему типу и bindings.

Exchange сам не является очередью и не хранит сообщения в ожидании consumer. Наличие binding ещё не означает,
что любое сообщение попадёт в связанную очередь: должны выполняться правила маршрутизации.

Если несколько bindings одной очереди подходят одной публикации, в рамках этой маршрутизации очередь получает
сообщение один раз. Независимые копии в разных очередях означают независимый учёт доставки; физическое
хранение тела может быть общим.

<a id="основные-типы-exchanges"></a>

#### [Основные типы exchanges](#содержание)

| Тип | Правило маршрутизации |
| --- | --- |
| **direct** | Routing key сообщения точно совпадает с ключом binding |
| **fanout** | Сообщение направляется во все привязанные очереди; routing key игнорируется |
| **topic** | Routing key соответствует шаблону binding |
| **headers** | Маршрутизация по заголовкам и условиям binding, а не по routing key |

**Direct** может направить сообщение в несколько очередей, если у них подходящие bindings. Это не механизм
выбора одного consumer.

У **topic** ключ состоит из частей, разделённых точками:

- `*` заменяет ровно одну часть;

- `#` заменяет ноль или больше частей.

| Binding | Подходит | Не подходит |
| --- | --- | --- |
| `entity.*` | `entity.created` | `entity.eu.created`, `entity` |
| `entity.#` | `entity`, `entity.created`, `entity.eu.created` | `other.created` |

Для **headers** обычно используют `x-match=all` — должны совпасть все заданные условия, или `x-match=any` —
достаточно одного.

<a id="default-exchange"></a>

#### [Default exchange](#содержание)

Встроенный **default exchange** — direct exchange с именем `""`. Каждая объявленная очередь автоматически
привязывается к нему с ключом, равным своему имени.

Поэтому публикация с пустым именем exchange и routing key, равным имени существующей очереди, направляется в
эту очередь. Это специальное правило default exchange; у пользовательских exchanges bindings задают явно.

<a id="если-подходящей-очереди-нет"></a>

#### [Если подходящей очереди нет](#содержание)

При обычной публикации без дополнительных настроек сообщение, для которого нет маршрута, отбрасывается. Флаг
публикации **mandatory** позволяет получить возврат такого сообщения через `basic.return`. Приложению нужно
обрабатывать эти возвраты.

<a id="4-очереди-и-потребители"></a>

### [4. Очереди и потребители](#содержание)

<a id="push-и-pull"></a>

#### [Push и pull](#содержание)

Основной способ потребления — подписка через **basic.consume**. После регистрации consumer брокер сам
отправляет ему сообщения: это **push-модель**. Одного открытого connection для получения сообщений
недостаточно.

Есть и получение по запросу — **basic.get**. Приложение запрашивает очередное сообщение самостоятельно; это
pull-вариант, который не стоит путать с обычной подпиской.

<a id="рассылка-между-очередями-и-распределение-внутри-очереди"></a>

#### [Рассылка между очередями и распределение внутри очереди](#содержание)

```text
                       ┌→ Queue X   → Consumer F
Publisher → Exchange ──┤
                       └→ Queue Y ─┬→ Consumer A
                                  └→ Consumer B
```

Если сообщение подходит обеим очередям, в каждой появляется своя копия. Обработка и подтверждение одной копии
не влияют на другую.

Если одну очередь слушают несколько обычных consumers, они **конкурируют за сообщения**. Конкретная доставка
назначается одному consumer. Получателя выбирает брокер с учётом доступности, prefetch и настроек
потребителей. При повторной доставке то же сообщение может получить другой consumer.

Отсюда два способа организации:

- **Разделение работы:** несколько экземпляров обработчика читают одну очередь.

- **Независимая обработка события разными сервисами:** у каждого сервиса своя очередь с подходящим binding.

<a id="порядок-сообщений"></a>

#### [Порядок сообщений](#содержание)

Очередь в основе работает по FIFO, но порядок завершения обработки не гарантирован: consumers могут
обрабатывать сообщения с разной скоростью. Приоритеты и повторные доставки также влияют на наблюдаемый
порядок.

<a id="5-подтверждения-и-состояния-сообщения"></a>

### [5. Подтверждения и состояния сообщения](#содержание)

Подтверждения нужны на двух независимых участках:

```text
Publisher ── публикация ──→ RabbitMQ ── доставка ──→ Consumer
Publisher ←── confirm ──── RabbitMQ ←── ack/nack ── Consumer
```

<a id="consumer-acknowledgements"></a>

#### [Consumer acknowledgements](#содержание)

В режиме **manual ack** consumer явно подтверждает результат обработки.

| Действие | Результат |
| --- | --- |
| `basic.ack` | Брокер может удалить сообщение из этой очереди |
| `basic.nack`, `requeue=true` | Сообщение возвращается в очередь для повторной доставки |
| `basic.nack`, `requeue=false` | Сообщение не возвращается в исходную очередь: отправляется в DLX, если он настроен, иначе отбрасывается |
| `basic.reject` | Отказ от одной доставки; также поддерживает `requeue` |

У `basic.nack` есть параметр **multiple**: он позволяет отклонить сразу несколько доставок. Аналогичный
параметр есть у `basic.ack`.

Подтверждение относится к **delivery tag** — идентификатору доставки в пределах channel. Подтверждать доставку
нужно на том же channel, на котором она была получена. При `multiple=true` действие охватывает
неподтверждённые доставки с тегами до указанного включительно на этом channel.

**Requeue не означает возврат в конец очереди.** Сообщение стараются вернуть на прежнюю позицию, а если это
невозможно — ближе к началу. Оно может сразу прийти повторно. Сам по себе `nack` не задаёт задержку повтора.

Если channel или connection закрывается, неподтверждённые доставки при ручном режиме возвращаются в очередь
для повторной доставки после обнаружения закрытия брокером.

В режиме **auto ack** брокер считает сообщение доставленным без явного подтверждения приложения. Это не
подтверждение успешной бизнес-обработки: если приложение упадёт после доставки, сообщение может быть потеряно
для обработки.

<a id="состояния-сообщения-в-очереди"></a>

#### [Состояния сообщения в очереди](#содержание)

```text
ready ── доставка ──→ unacked ── ack ──→ удаление
  ↑                     │
  └──── requeue ─────────┘
```

- **Ready** — сообщение ожидает доставки.

- **Unacked** — доставлено, но ещё не подтверждено в ручном режиме.

- После `ack` сообщение больше не предназначено для чтения из этой очереди.

<a id="publisher-confirms"></a>

#### [Publisher confirms](#содержание)

**Publisher confirms** — подтверждения от брокера отправителю. Режим включается отдельно для channel.

Confirm сообщает о результате приёма публикации брокером согласно используемому типу очереди и настройкам
хранения. Он **не подтверждает обработку consumer**.

Положительный confirm сам по себе также не доказывает, что нашлась подходящая очередь: публикация без маршрута
тоже может быть подтверждена. Для обнаружения отсутствующего маршрута используют `mandatory` и обработку
возвратов.

<a id="6-prefetch-и-управление-нагрузкой"></a>

### [6. Prefetch и управление нагрузкой](#содержание)

**Prefetch** ограничивает число доставок, которые могут оставаться неподтверждёнными. Его задают через
`basic.qos`.

В RabbitMQ при обычной настройке с `global=false` лимит применяется отдельно к каждому новому consumer на
channel. Например, `prefetch=10` позволяет consumer иметь до десяти неподтверждённых сообщений. Когда лимит
достигнут, новые доставки ожидают освобождения места после подтверждений.

- Малый prefetch может ограничивать производительность.

- Большой prefetch увеличивает объём сообщений в обработке и может ухудшать распределение работы между consumers.

- Значение `0` означает отсутствие лимита prefetch.

Prefetch полезен при ручных подтверждениях; в режиме auto ack он не ограничивает число сообщений, ожидающих
завершения бизнес-обработки. Он также не задаёт количество goroutines: параллелизм обработчиков приложение
организует отдельно.

<a id="7-хранение-и-надёжность"></a>

### [7. Хранение и надёжность](#содержание)

RabbitMQ может хранить сообщения на диске. Удаление после `ack` — свойство обычной очереди, а не определение
брокера сообщений.

<a id="где-физически-находятся-сообщения"></a>

#### [Где физически находятся сообщения](#содержание)

**RabbitMQ использует и оперативную память, и диск.** Это ресурсы сервера или контейнера с брокером, а не
память Go-приложения publisher. После доставки у consumer появляется свой экземпляр данных в памяти
приложения.

```text
Go publisher                 Сервер RabbitMQ                 Go consumer
память приложения ── сеть ──→ RAM: буферы, кэш, метаданные ──→ память приложения
                             Диск: хранилище очередей
```

Конкретное размещение зависит от типа очереди, версии RabbitMQ, свойств сообщения и того, насколько быстро оно
потребляется. Сообщение может одновременно иметь запись на диске и представление в памяти.

Современные **classic queues** используют дисковое хранилище, оставляя часть данных в RAM для быстрой
доставки. **Quorum queues** используют журнал на диске и репликацию. Память нужна обоим типам: для буферов,
кэшей, метаданных и текущих операций.

Детали внутреннего хранения менялись между версиями, поэтому правило «очередь целиком в RAM, а на диск идёт
только при нехватке памяти» не подходит как общая модель. См. [устройство classic
queues](https://www.rabbitmq.com/docs/classic-queues) и [quorum
queues](https://www.rabbitmq.com/docs/quorum-queues).

Разделяй два вопроса:

1. **Где сейчас находятся байты?** Это вопрос реализации хранения и кэширования.

2. **Должно ли сообщение пережить перезапуск?** Это вопрос свойств очереди, сообщения и подтверждений.

`Persistent` не означает «сообщение существует только на диске», а `transient` не означает «оно никогда не
записывается на диск». Даже временные сообщения могут использовать диск; это само по себе не даёт гарантии
восстановления. См. [описание persistence](https://www.rabbitmq.com/docs/persistence-conf).

Если RabbitMQ работает в Docker, файлы находятся в файловой системе контейнера или подключённого volume.
Durable и persistent не спасут данные, если удалить само хранилище. Для сохранения при пересоздании контейнера
каталог данных брокера должен размещаться на сохраняемом volume.

<a id="durable-сохраняем-саму-очередь"></a>

#### [Durable: сохраняем саму очередь](#содержание)

Очередь — сущность с именем, настройками и учётом сообщений. `durable=true` означает, что её объявление должно
пережить перезапуск брокера. После запуска очередь с прежним именем снова существует.

`durable=false` означает временную очередь, которая не переживает перезапуск. Поддержка отдельных вариантов
временных очередей зависит от версии и конфигурации RabbitMQ; это не рекомендуемая настройка по умолчанию для
важных событий.

Аналогия: очередь — почтовый ящик, сообщения — письма. Durable сохраняет ящик. Что будет с письмами,
определяется отдельно.

Поэтому фраза «очередь durable, значит все сообщения точно сохранятся» неверна. Кроме того, durable не
отменяет удаление очереди администратором, auto-delete или другие правила её жизненного цикла.

<a id="настройки-жизненного-цикла-очереди"></a>

#### [Настройки жизненного цикла очереди](#содержание)

| Настройка | Значение |
| --- | --- |
| **durable** | Очередь сохраняется после перезапуска брокера |
| **exclusive** | Очередь доступна только объявившему её connection и удаляется при его закрытии |
| **auto-delete** | Очередь удаляется после исчезновения последнего consumer, если consumer у неё уже был |

У exchange также есть `durable`: это сохранение самого exchange, а не сообщений внутри него.

<a id="persistent-messages"></a>

#### [Persistent messages](#содержание)

**Persistent** — свойство сообщения (`delivery_mode=2`), выражающее требование устойчивого хранения.
`delivery_mode=1` означает transient-сообщение, восстановление которого после перезапуска не гарантируется.

Для durable **classic queue** базовое сочетание для восстановления — durable-очередь и persistent-сообщение:

| Очередь | Сообщение | Что ожидаем при перезапуске брокера с сохранённым диском |
| --- | --- | --- |
| Не durable | Любое | Сама очередь не восстановится |
| Durable | Transient | Очередь восстановится; на восстановление сообщения рассчитывать нельзя |
| Durable | Persistent | Сообщение предназначено для восстановления вместе с очередью; publisher должен дождаться confirm |

Это таблица про classic queues. Quorum queues всегда durable и сохраняют сообщения независимо от
`delivery_mode`.

Сохранение сообщения не означает, что оно хранится навечно: после consumer ack оно больше не должно выдаваться
этой очередью. TTL и другие правила удаления тоже продолжают действовать.

Одной настройки `durable` недостаточно для надёжности всей доставки. Publisher должен получать confirms,
consumer — подтверждать завершённую обработку, а приложение — учитывать повторы.

<a id="classic-и-quorum-queues"></a>

#### [Classic и quorum queues](#содержание)

- **Classic queue** — обычная очередь без репликации между узлами.

- **Quorum queue** — реплицируемая очередь, использующая согласование на основе Raft; для работы требуется большинство её реплик.

Наличие кластера само по себе не означает, что каждая очередь реплицирована. Устойчивость к перезапуску и
устойчивость к потере узла — разные свойства.

<a id="гарантии-доставки"></a>

#### [Гарантии доставки](#содержание)

- **At-most-once** — допускаются потери, повторную доставку не обеспечивают.

- **At-least-once** — доставка обеспечивается с возможными повторами при соответствующей настройке брокера и приложений.

- **Exactly-once для бизнес-эффекта** не появляется автоматически из `ack` и confirms.

Надёжное использование RabbitMQ обычно строят с учётом возможной повторной доставки. **Идемпотентность
обработчика** означает, что повторная обработка одного события не приводит к повторному бизнес-эффекту.
Конкретные способы её реализации — следующий этап изучения.

<a id="8-ttl-и-dead-lettering"></a>

### [8. TTL и dead lettering](#содержание)

**Message TTL** ограничивает время жизни сообщения в очереди. Его можно задать для очереди или отдельного
сообщения. Это не таймаут выполнения обработчика.

**Dead-letter exchange, DLX** — обычный exchange, в который брокер перепубликует сообщения из очереди при
определённых условиях, например:

- consumer отказался от сообщения с `requeue=false`;

- истёк TTL сообщения;

- превышен лимит длины очереди при соответствующей политике переполнения;

- превышен лимит доставок quorum queue.

DLX настраивают для исходной очереди через policy или аргументы объявления. Отдельную очередь, привязанную к
DLX для сбора таких сообщений, часто называют **dead-letter queue, DLQ**.

```text
Исходная очередь ── dead lettering ──→ DLX ── binding ──→ DLQ
```

DLX и DLQ — разные сущности. Наличие DLX само по себе не создаёт очередь для хранения отклонённых сообщений и
не обеспечивает автоматический повтор обработки с задержкой.

<a id="9-кластеризация"></a>

### [9. Кластеризация](#содержание)

<a id="что-такое-кластер-и-как-узлы-взаимодействуют"></a>

#### [Что такое кластер и как узлы взаимодействуют](#содержание)

**Кластер RabbitMQ** — несколько запущенных экземпляров брокера, объединённых настройкой в одну систему.
Каждый экземпляр называется **узлом (node)**. У него свои RAM, диск и сетевые соединения.

Узлы взаимодействуют по сети: отправляют команды и данные, принимают их, выполняют локальные действия
и возвращают ответы. Общая оперативная память для этого не нужна. Для первоначального объединения
используется **peer discovery** — обнаружение других узлов.

```text
Машина A                 Машина B                 Машина C
┌───────────────┐        ┌───────────────┐        ┌───────────────┐
│ RabbitMQ A    │◄──────►│ RabbitMQ B    │◄──────►│ RabbitMQ C    │
│ RAM + диск    │        │ RAM + диск    │        │ RAM + диск    │
└───────────────┘        └───────────────┘        └───────────────┘
        ▲                                                ▲
        └────────────────── сеть ────────────────────────┘
```

Три контейнера на одном сервере позволяют изучить взаимодействие процессов, но все зависят от этого
сервера. Размещение на разных машинах позволяет пережить отказ одной машины при подходящей репликации.

<a id="основные-термины-кластеризации"></a>

#### [Основные термины кластеризации](#содержание)

| Термин | Значение |
| --- | --- |
| **Node** | Отдельный процесс RabbitMQ со своим именем, памятью и диском |
| **Cluster** | Узлы RabbitMQ, объединённые в одну систему |
| **Peer discovery** | Механизм поиска узлов для формирования кластера |
| **Replication** | Поддержание копий состояния на нескольких узлах |
| **Queue replica** | Локальное состояние конкретной очереди на одном узле |
| **Leader** | Реплика quorum queue, координирующая её операции |
| **Follower** | Реплика quorum queue, получающая изменения от лидера |
| **Quorum** | Большинство участников группы реплик, необходимое для согласования |
| **Failover** | Переход к работе через доступные компоненты после отказа |
| **Network partition** | Разрыв связи между частями системы, хотя сами процессы могут продолжать работать |

Не путать **реплику приложения**, которая исполняет код, и **реплику очереди**, которая участвует
в хранении и согласовании состояния. Их количество и назначение независимы.

<a id="общее-пространство-сущностей-и-репликация-сообщений"></a>

#### [Общее пространство сущностей и репликация сообщений](#содержание)

Внутри одного vhost узлы кластера предоставляют общее пространство exchanges, очередей и bindings.
Объявление очереди с одним именем через разные узлы не создаёт отдельную очередь на каждом из них.

Но общая видимость сущности не означает, что её сообщения скопированы на все узлы:

- **Classic queue** в современных RabbitMQ не реплицируется между узлами.

- **Quorum queue** имеет группу реплик, использующую Raft. Не обязательно каждый узел кластера входит
  в группу реплик каждой очереди.

Сначала формируют кластер, затем отдельно выбирают тип и размещение очередей. Добавление узла
в существующий кластер само по себе не гарантирует добавления реплики каждой старой quorum queue:
состав групп реплик управляется отдельно.

<a id="лидер-конкретной-очереди-и-большинство"></a>

#### [Лидер конкретной очереди и большинство](#содержание)

У каждой quorum queue свой leader. Это не один главный брокер для всех сообщений кластера.
Роли управления метаданными кластера — отдельный механизм; их не нужно смешивать с лидерами очередей.

```text
                         Node A       Node B       Node C
Quorum queue Q1          Leader       Follower     Follower
Quorum queue Q2          Follower     Leader       Follower
```

Leader передаёт изменения followers и получает ответы. Для согласования необходимо большинство
**реплик этой очереди**: `floor(N / 2) + 1` при общем числе реплик N.

Для трёх реплик большинство — две. Потеря одного узла допускает выбор нового лидера и продолжение
работы; потеря двух лишает очередь большинства. Потерю сетевой связи также нужно учитывать:
одиночная изолированная реплика не может продолжать принимать изменения как независимый лидер.

Репликация повышает отказоустойчивость, но требует сетевого и дискового обмена. Три реплики одной
очереди не превращают её в три независимых потока работы и не обещают трёхкратный рост производительности.

<a id="подключение-приложения-к-узлу-без-лидера-очереди"></a>

#### [Подключение приложения к узлу без лидера очереди](#содержание)

Для AMQP 0-9-1 приложение может подключиться к доступному узлу, а RabbitMQ направит операции
к лидеру нужной очереди внутри кластера. Клиенту не нужно отслеживать размещение лидеров.

```text
Приложение ── connection ──→ Node A ── межузловой обмен ──→ Node B
                            входной узел                  лидер Q1
```

Это передача операций внутри кластера, а не перенаправление TCP-соединения клиента на другой узел.
Ответы клиент получает через своё исходное соединение. Доставка consumer и его ack тоже могут
требовать межузлового обмена.

Можно постоянно использовать один входной узел, пока он доступен и справляется с нагрузкой.
Но единственный адрес создаёт зависимость приложения от этой машины, даже если очередь пережила
её отказ. Все подключения через один узел также нагружают его сеть и ресурсы.

Поэтому приложениям дают несколько адресов для выбора и восстановления или адрес TCP-балансировщика.
При этом **для каждого сообщения новое подключение не выбирают**: обычно используют долгоживущий connection.
Балансировщик тоже не переносит уже установленное TCP-соединение при отказе узла.

<a id="копии-приложения-и-восстановление-после-отказа"></a>

#### [Копии приложения и восстановление после отказа](#содержание)

Несколько экземпляров одного обработчика подписываются на одну очередь в одном vhost. Брокер
распределяет доставки между consumers независимо от того, к каким узлам они подключились.
Привязывать worker к физической реплике очереди не требуется.

Разделяй два уровня восстановления:

| Уровень | Что происходит |
| --- | --- |
| Очередь | Оставшиеся реплики при наличии большинства выбирают нового лидера |
| Приложение | После потери connection подключается к доступному узлу, открывает channels и восстанавливает подписки |

Выбор лидера не восстанавливает TCP-соединения. Клиентский код или используемая библиотека должны
реализовать повторное подключение, восстановление QoS, confirms и подписок. Возможны пауза в работе,
неопределённый результат публикации и повторные доставки — идемпотентность по-прежнему нужна.

Связанные источники: [clustering](https://www.rabbitmq.com/docs/clustering),
[quorum queues](https://www.rabbitmq.com/docs/quorum-queues),
[peer discovery](https://www.rabbitmq.com/docs/cluster-formation).

<a id="10-краткая-модель-для-повторения"></a>

### [10. Краткая модель для повторения](#содержание)

1. Приложение открывает connection и channels, объявляет необходимую топологию.

2. Publisher публикует сообщение в exchange с routing key.

3. Exchange выбирает очереди по своему типу и bindings.

4. Каждая подходящая очередь получает свою копию сообщения.

5. Брокер доставляет сообщения зарегистрированным consumers с учётом prefetch.

6. Consumers одной очереди делят работу; consumers разных очередей обрабатывают независимые копии.

7. В ручном режиме сообщение остаётся `unacked` до подтверждения или возврата.

8. Consumer ack подтверждает обработку брокеру; publisher confirm подтверждает публикацию отправителю.

9. Хранение, репликация, подтверждения и обработка повторов решают разные части задачи надёжности.

<a id="часть-ii-примеры-настройки-и-использования"></a>

## [Часть II. Примеры настройки и использования](#содержание)

Все определения выше применимы независимо от предметной области. Здесь магазин, `feed` и `orders` используются
для демонстрации. Варианты exchanges показаны как самостоятельные схемы; их не нужно одновременно подключать к
одним очередям для повторения примера.

<a id="сквозной-пример-заказ-и-лента-событий"></a>

### [Сквозной пример: заказ и лента событий](#содержание)

Представим магазин с двумя обработчиками:

- обработчик `orders` запускает подготовку созданного заказа;

- обработчик `feed` добавляет запись о заказе в ленту пользователя.

Приложение публикует событие:

```text
exchange:    shop.events
routing key: orders.created
body:        {"event_id":"evt-101","order_id":42,"user_id":7}
```

Здесь `shop.events` — имя exchange, `orders.created` — ключ маршрутизации, JSON — тело сообщения. Это три
разных части публикации. Имя очереди publisher в этом примере вообще не указывает.

Если настроить нужные bindings, событие попадёт и в очередь `orders`, и в очередь `feed`. Обработчики читают
каждый свою очередь. Даже если сервис ленты временно выключен, очередь `feed` может накапливать события до его
возвращения.

Название очереди произвольно: очередь `feed` может получать сообщения с ключом `orders.created`. RabbitMQ не
выводит правила из названий — их задают явно.

<a id="публикация-через-default-exchange"></a>

### [Публикация через default exchange](#содержание)

```text
exchange="", routing_key="orders" → существующая очередь orders
```

Никакой пользовательский binding для этого маршрута создавать не требуется: он появляется автоматически при
объявлении очереди.

<a id="пример-fanout-одно-событие-нужно-и-feed-и-orders"></a>

### [Пример fanout: одно событие нужно и feed, и orders](#содержание)

Создадим exchange `shop.broadcast` типа `fanout` и привяжем к нему две очереди:

```text
                                  ┌──→ orders → обработчик заказов
Publisher → shop.broadcast fanout ┤
                                  └──→ feed   → обработчик ленты
```

Публикуем сообщение о заказе №42. Оно попадает в обе очереди. Для `fanout` ключ `orders.created` не влияет на
выбор: любое сообщение в этом exchange направляется в обе очереди.

Такой exchange удобен, когда всем привязанным очередям нужны все события потока. Если `feed` должен получать
только часть событий, нужен другой тип маршрутизации или отдельный поток публикаций.

<a id="пример-direct-точный-выбор-по-ключу"></a>

### [Пример direct: точный выбор по ключу](#содержание)

Объявим **другой** exchange `shop.direct` типа `direct`. В следующих примерах тип exchange не меняется на
месте: это отдельные варианты схемы.

Bindings:

| Откуда | Binding key | Куда |
| --- | --- | --- |
| `shop.direct` | `orders.created` | `orders` |
| `shop.direct` | `orders.created` | `feed` |
| `shop.direct` | `posts.created` | `feed` |

Результат публикаций:

| Routing key сообщения | Очередь orders | Очередь feed |
| --- | --- | --- |
| `orders.created` | Получит | Получит |
| `posts.created` | Не получит | Получит |
| `orders.cancelled` | Не получит | Не получит |

Binding можно прочитать как правило: «Из `shop.direct` направляй в `feed` сообщения, чей routing key равен
`orders.created`».

У `feed` два bindings, потому что ей нужны два разных вида событий. Ключ `orders.created` совпадает с bindings
обеих очередей, поэтому `direct` отправит сообщение в обе. `Direct` означает точное сравнение ключей, а не
доставку в одну очередь.

<a id="пример-topic-подписка-на-семейство-событий"></a>

### [Пример topic: подписка на семейство событий](#содержание)

Объявим exchange `shop.events` типа `topic`:

| Очередь | Шаблон binding | Что хотим получать |
| --- | --- | --- |
| `orders` | `orders.#` | Все события о заказах |
| `feed` | `*.created` | События создания с ключом из двух частей |

Проверим конкретные публикации:

| Routing key | orders | feed | Почему |
| --- | --- | --- | --- |
| `orders.created` | Да | Да | Подходит обоим шаблонам |
| `orders.cancelled` | Да | Нет | Для feed вторая часть должна быть created |
| `posts.created` | Нет | Да | Для orders первая часть должна быть orders |
| `orders.eu.created` | Да | Нет | У ключа три части, а `*.created` ожидает две |
| `orders` | Да | Нет | `#` может заменить ноль частей |

Сама очередь `orders` не анализирует routing key: сообщение уже выбрано exchange и помещено в очередь.

Если два bindings одной очереди подходят одному сообщению, это не создаёт две доставки в эту очередь в рамках
одной маршрутизации. Под «копией в каждой очереди» понимается независимый учёт сообщения; физическое хранение
тела может быть общим.

<a id="пример-headers-отбор-по-нескольким-признакам"></a>

### [Пример headers: отбор по нескольким признакам](#содержание)

Допустим, в exchange `shop.headers` публикуют сообщения с заголовками:

```text
region: eu
format: json
```

Привяжем `feed` с аргументами `x-match=all`, `region=eu`, `format=json`. Сообщение с этими двумя значениями
попадёт в `feed`, а с `region=us` — нет. При `x-match=any` достаточно совпадения одного из условий.

Такой exchange позволяет маршрутизировать по нескольким метаданным без составления единственного routing key.
Тело JSON при этом exchange не разбирает.

<a id="настройка-топологии-из-go-приложения"></a>

### [Настройка топологии из Go-приложения](#содержание)

Используем `github.com/rabbitmq/amqp091-go` с именем импорта `amqp`. Ниже функция подготовки: она открывает
connection и два channels, объявляет durable topic exchange, classic queues и bindings. При ошибке освобождает
уже открытые ресурсы. При успехе владение ресурсами получает вызывающий код.

```go
func setup(url string) (
    conn *amqp.Connection,
    pubCh, consumeCh *amqp.Channel,
    err error,
) {
    conn, err = amqp.Dial(url)
    if err != nil {
        return
    }
    defer func() {
        if err != nil {
            conn.Close()
        }
    }()

    pubCh, err = conn.Channel()
    if err != nil {
        return
    }
    consumeCh, err = conn.Channel()
    if err != nil {
        return
    }

    err = pubCh.ExchangeDeclare(
        "shop.events", "topic",
        true, false, false, false, nil,
    ) // durable, autoDelete, internal, noWait, args
    if err != nil {
        return
    }

    for _, binding := range []struct{ queue, key string }{
        {"orders", "orders.#"},
        {"feed", "*.created"},
    } {
        _, err = pubCh.QueueDeclare(
            binding.queue, true, false, false, false,
            amqp.Table{"x-queue-type": "classic"},
        ) // name, durable, autoDelete, exclusive, noWait, args
        if err != nil {
            return
        }
        err = pubCh.QueueBind(
            binding.queue, binding.key, "shop.events", false, nil,
        ) // queue, binding key, exchange, noWait, args
        if err != nil {
            return
        }
    }
    err = consumeCh.Qos(10, 0, false)
    return
}
```

После успешного возврата схема выглядит так:

```text
Go-приложение                         RabbitMQ
Connection
├── pubCh ── публикации ────────────→ shop.events (topic)
│                                    ├─ orders.#  → orders
│                                    └─ *.created → feed
└── consumeCh ←─ доставки ───────────────────────── orders
              └─ ack ────────────────────────────→ брокер
```

Через `pubCh` объявлены обе очереди, но это не делает их собственностью `pubCh`. Другой процесс может
подключиться и читать `feed` через свой channel.

Далее приложение может вызвать `pubCh.Publish(...)` с exchange `shop.events` и ключом `orders.created`, а
через `consumeCh.Consume(...)` зарегистрировать подписку на `orders` с `autoAck=false`. Возвращённый
библиотекой Go-канал с доставками читает код обработчика.

Вызов `delivery.Ack(false)` отправляет ack через AMQP channel, на котором была получена доставка.

Это пример объявления топологии и разделения channels. Для надёжного publisher отдельно настраивают confirms и
обработку возвратов, а для жизненного цикла приложения — восстановление соединения и корректную остановку.
Вызывающий код закрывает оба channels и connection, когда работа завершена.

<a id="пример-два-события-три-обработчика"></a>

### [Пример: два события, три обработчика](#содержание)

Пусть `orders.created` направляется и в `orders`, и в `feed`. Опубликуем события для заказов №42 и №43.

Одно из возможных распределений:

```text
orders: заказ №42 → Consumer A
        заказ №43 → Consumer B

feed:   заказ №42 → Consumer F
        заказ №43 → Consumer F
```

A и B не должны оба получить каждое событие при обычной доставке: они обслуживают одну очередь и делят работу.
F получает оба события, потому что читает отдельную очередь.

Если F остановлен, сообщения остаются ждать в `feed`, пока настройки очереди позволяют их хранить. A и B
продолжают работать с `orders` независимо.

Если очередь `feed` вообще не была создана и привязана в момент публикации, создание её позже не воспроизведёт
старые события: exchange не хранит историю для будущих очередей.

<a id="пример-жизненного-цикла-одного-сообщения"></a>

### [Пример жизненного цикла одного сообщения](#содержание)

В очередь `orders` пришло событие о заказе №42. Других сообщений нет, используется manual ack:

| Момент | Ready | Unacked | Что произошло |
| --- | --- | --- | --- |
| Consumer ещё не получил событие | 1 | 0 | Сообщение ждёт в очереди |
| Событие доставлено Consumer A | 0 | 1 | Брокер ждёт подтверждения |
| A закончил обработку и отправил ack | 0 | 0 | Обязательство очереди по этой доставке завершено |

Если вместо ack отправить `nack` с `requeue=true`, сообщение снова доступно для доставки. Оно может почти
сразу перейти в `unacked` у A или B, поэтому состояние `ready=1` не обязательно получится заметить в
интерфейсе.

`Ready` и `unacked` — состояния доставки, а не указание, лежит тело сообщения в RAM или на диске. После ack
место в дисковых файлах может освобождаться позже при внутренней очистке.

<a id="пример-prefetch"></a>

### [Пример prefetch](#содержание)

У Consumer A стоит `prefetch=2`, manual ack, а в очереди лежат пять сообщений. Если у очереди нет других
consumers:

```text
A получил №1 и №2 → unacked=2, ready=3.
A подтвердил №1   → освободилось одно место.
Брокер выдал №3   → unacked=2, ready=2.
```

Это не означает, что A обрабатывает два сообщения одновременно. Он может разбирать их последовательно или
использовать ограниченный пул goroutines. Важно подтверждать сообщение после завершения нужной обработки,
иначе prefetch перестанет отражать реальную нагрузку.

<a id="пример-заказ-опубликован-обработчик-пока-выключен"></a>

### [Пример: заказ опубликован, обработчик пока выключен](#содержание)

Предположим, используем classic queue `orders`:

1. Объявляем `orders` с `durable=true` и нужный durable exchange с binding.

2. Публикуем событие о заказе №42 с `delivery_mode=2`.

3. Ждём положительного publisher confirm: для persistent-сообщения в durable classic queue подтверждение учитывает запись на диск.

4. Consumer пока выключен, поэтому сообщение ждёт доставки.

5. Перезапускаем RabbitMQ с сохранённым каталогом данных. Очередь и сообщение восстанавливаются.

6. Запускаем consumer, он получает событие, обрабатывает и отправляет ack.

7. Сообщение удаляется из очереди, хотя было persistent.

Если положительный confirm не получен, publisher не знает, успел ли брокер принять публикацию. Если потерян
сам диск с единственной classic queue, durable и persistent не восстановят его содержимое. Репликация решает
отдельную задачу — сохранение копий на других узлах.

<a id="пример-dlx-для-очереди-orders"></a>

### [Пример DLX для очереди orders](#содержание)

```text
shop.events → orders → consumer
                 │
                 └── nack(requeue=false) → shop.dead → orders.dlq
```

Для `orders` задаём DLX `shop.dead` и dead-letter routing key `orders.failed`. Сам `shop.dead` объявляем как
direct exchange, а очередь `orders.dlq` привязываем с ключом `orders.failed`.

Тогда отказ от обработки с `requeue=false` направит сообщение в `orders.dlq`. Если выбрать `requeue=true`, оно
вернётся в `orders`, а не отправится по этому маршруту в DLX. На базовом уровне считаем, что лимиты повторных
доставок и другие дополнительные условия не сработали.

Например, неверный формат события можно направить в DLQ для разбора. Если очередь DLQ или подходящий binding
отсутствуют, один только DLX не обеспечит сохранение сообщения.

<a id="пример-кластер-rabbitmq-на-трёх-машинах"></a>

### [Пример: кластер RabbitMQ на трёх машинах](#содержание)

Это учебная последовательность для **трёх новых Linux-узлов с пакетной установкой RabbitMQ**,
до первого запуска брокеров. Используем одну совместимую версию RabbitMQ и Erlang на всех машинах.
Подготовленные пути и команды ниже относятся к обычной пакетной установке с systemd.

<a id="шаг-1-подготовить-машины-и-имена"></a>

#### [Шаг 1. Подготовить машины и имена](#содержание)

| Машина / hostname | IP | Имя RabbitMQ-узла |
| --- | --- | --- |
| rmq1 | 10.0.0.11 | rabbit@rmq1 |
| rmq2 | 10.0.0.12 | rabbit@rmq2 |
| rmq3 | 10.0.0.13 | rabbit@rmq3 |

Каждая машина должна разрешать имена всех остальных. Например, на всех трёх в `/etc/hosts`:

```text
10.0.0.11 rmq1
10.0.0.12 rmq2
10.0.0.13 rmq3
```

Собственный hostname каждой машины должен соответствовать таблице. В этой схеме используются
короткие имена; полные доменные имена требуют согласованной настройки long node names.
У каждой машины свой сохраняемый каталог данных: общий сетевой каталог для трёх узлов не нужен.

<a id="шаг-2-обеспечить-сетевую-доступность"></a>

#### [Шаг 2. Обеспечить сетевую доступность](#содержание)

| TCP-порт по умолчанию | Кто использует |
| --- | --- |
| 5672 | Приложения для AMQP без TLS |
| 4369 | Узлы и CLI для обнаружения порта Erlang-процесса |
| 25672 | Узлы RabbitMQ для межузлового взаимодействия |

Между всеми тремя машинами разрешают 4369 и 25672, а приложениям дают доступ к клиентскому порту.
Кластерные порты оставляют во внутренней сети. Management UI и TLS используют отдельные порты,
они не требуются для понимания этого примера. Подробнее: [networking](https://www.rabbitmq.com/docs/networking).

<a id="шаг-3-настроить-общий-erlang-cookie"></a>

#### [Шаг 3. Настроить общий Erlang cookie](#содержание)

В `/var/lib/rabbitmq/.erlang.cookie` на всех трёх машинах помещают **одну и ту же случайную секретную
строку**. Это секрет аутентификации узлов между собой, а не пароль прикладного AMQP-пользователя.

После записи файла на каждой машине:

```bash
sudo chown rabbitmq:rabbitmq /var/lib/rabbitmq/.erlang.cookie
sudo chmod 600 /var/lib/rabbitmq/.erlang.cookie
```

Значение нужно подготовить до запуска и обеспечить его совпадение. Команды CLI тоже должны использовать
совпадающий cookie; запуск от пользователя `rabbitmq` ниже позволяет использовать его файл.

<a id="шаг-4-указать-список-узлов"></a>

#### [Шаг 4. Указать список узлов](#содержание)

На каждой машине в `/etc/rabbitmq/rabbitmq.conf`:

```ini
cluster_formation.peer_discovery_backend = classic_config

cluster_formation.classic_config.nodes.1 = rabbit@rmq1
cluster_formation.classic_config.nodes.2 = rabbit@rmq2
cluster_formation.classic_config.nodes.3 = rabbit@rmq3
```

Это список кандидатов для формирования кластера, а не назначения лидеров очередей.
`classic_config` — название способа обнаружения; оно не задаёт тип classic queue.
Настройка предназначена для первичного объединения новых узлов. Правка файла на трёх уже работающих
независимых брокерах не объединяет автоматически их существующие данные.

<a id="шаг-5-запустить-и-проверить-кластер"></a>

#### [Шаг 5. Запустить и проверить кластер](#содержание)

В этом сценарии сначала запускаем rmq1, затем rmq2 и rmq3. На соответствующих машинах:

```bash
sudo systemctl start rabbitmq-server
```

Проверяем на одном из узлов:

```bash
sudo -u rabbitmq rabbitmqctl cluster_status
```

В списке работающих узлов ожидаем все три имени. Если каждый показывает только себя, кластер
не сформирован: проверяем разрешение имён, доступность портов, совпадение cookie и логи запуска.

Первый запущенный узел даёт точку присоединения, но не становится вечным лидером всех очередей.
Подробности формирования: [cluster formation](https://www.rabbitmq.com/docs/cluster-formation).

<a id="шаг-6-подготовить-доступ-приложения-и-quorum-queue"></a>

#### [Шаг 6. Подготовить доступ приложения и quorum queue](#содержание)

Администратор создаёт прикладного пользователя и vhost, выдаёт права configure/write/read на нужные
сущности. Встроенный `guest` по умолчанию не подходит для удалённого подключения.
Все копии приложения должны использовать нужный общий vhost и согласованные имена очередей.

Через открытый `*amqp.Channel` Go-приложение объявляет **новую** очередь:

```go
_, err := ch.QueueDeclare(
    "orders.quorum",
    true,  // durable
    false, // autoDelete
    false, // exclusive
    false, // noWait
    amqp.Table{
        "x-queue-type": "quorum",
        "x-quorum-initial-group-size": 3,
    },
)
if err != nil {
    return err
}
```

Используется `github.com/rabbitmq/amqp091-go` с именем импорта `amqp`. Фрагмент выполняется внутри
функции, возвращающей error. Очередь называется `orders.quorum`, чтобы не конфликтовать с classic
очередью `orders` из других примеров: тип существующей очереди таким объявлением не меняют.

При трёх доступных узлах будет создана группа из трёх реплик. Exchange и binding объявляют отдельно,
как в примере топологии выше. Quorum queue не требует собственного exchange на каждой машине.

<a id="шаг-7-подключить-копии-приложения"></a>

#### [Шаг 7. Подключить копии приложения](#содержание)

Возможный прикладной конфиг:

```yaml
rabbitmq:
  addresses:
    - amqp://app:password@rmq1:5672/
    - amqp://app:password@rmq2:5672/
    - amqp://app:password@rmq3:5672/
  queue: orders.quorum
```

Здесь показан vhost `/` и условные учётные данные. Это конфиг нашего приложения, а не формат,
который `amqp.Dial` самостоятельно прочитает. Выбор адреса и повторные подключения реализует
приложение или обёртка над клиентом. После подключения используют постоянный connection.

```text
Worker 1 → rmq1 ──┐
Worker 2 → rmq2 ──┼── одна логическая очередь orders.quorum
Worker 3 → rmq3 ──┘
```

Лидером этой очереди, например, оказался rmq2. Публикации через rmq1 и rmq3 RabbitMQ передаст ему
внутри кластера. Consumers распределяют работу одной очереди, а не читают независимые копии данных.

<a id="шаг-8-разобрать-отказ-одной-машины"></a>

#### [Шаг 8. Разобрать отказ одной машины](#содержание)

Предположим, лидер очереди находился на rmq2 и машина стала недоступна:

1. rmq1 и rmq3 обнаруживают потерю связи. У группы остаётся большинство — две реплики из трёх.

2. Для очереди выбирается новый лидер. Работа может приостановиться на время обнаружения и выборов.

3. Приложения, подключённые к rmq2, теряют connection и переподключаются к доступным адресам.

4. Они открывают новые channels, восстанавливают настройки и подписки. Неподтверждённые доставки
   могут прийти повторно; публикации без полученного confirm имеют неопределённый для publisher результат.

5. Вернувшийся узел с сохранённым состоянием и членством в группе догоняет актуальное состояние
   по протоколу репликации. Потеря его каталога данных — отдельный сценарий замены узла.

Если приложение знает только адрес rmq2, очередь может быть доступна, а приложение продолжит
безуспешно обращаться к выключенной машине. Отказоустойчивость очереди и восстановление доступа
приложения нужно проектировать вместе.
