# NATS и JetStream

**NATS** — система обмена сообщениями между приложениями. В основе лежит **Core NATS**: публикация в
именованные subjects и доставка заинтересованным подписчикам. **JetStream** — встроенная подсистема NATS для
хранения сообщений, повторного чтения и подтверждаемой доставки.

<a id="summary"></a>

## [Summary](#содержание)

Core NATS работает по модели **pub/sub с push-доставкой**. Publisher публикует сообщение в **subject** — адрес
вроде `orders.created`. Обычные subscribers с подходящей подпиской получают свои копии. Если несколько
subscribers объединены в **queue group**, конкретная доставка назначается одному участнику этой группы.

Core NATS не хранит историю и не ждет consumer ack. Если нет подходящего подключенного подписчика, сообщение
не будет ожидать его появления. Это **at-most-once**, а не надежная очередь заданий.

**JetStream включается в nats-server**, а не разворачивается как отдельный внешний брокер. Он добавляет
**stream** — серверное хранилище сообщений с выбранных subjects, и **consumer** — серверный объект, который
отслеживает доставку и подтверждения. Приложение публикует в subject, stream сохраняет запись, consumer
выбирает сообщения, а клиент получает и подтверждает их.

```text
Publisher → subject → Stream → Consumer → Go worker
                        ↑         ↑
                     хранение   состояние доставки
```

У stream есть FileStorage или MemoryStorage, ограничения объема/возраста и число replicas. Политика retention
определяет, удаляется ли сообщение из-за ack: **LimitsPolicy** хранит в рамках лимитов независимо от ack,
**InterestPolicy** учитывает всех заинтересованных consumers, **WorkQueuePolicy** удаляет после успешной
обработки одним consumer.

Несколько независимых consumers одного stream могут читать сообщения независимо при подходящей retention
policy. Несколько Go workers, использующих **один pull consumer**, делят его работу. Нельзя путать объект
consumer на сервере с отдельным экземпляром приложения.

JetStream поддерживает pull и push consumers. Для обычного масштабируемого worker удобен **durable pull
consumer с AckExplicit**: worker запрашивает сообщения и подтверждает каждое после обработки. Durable
сохраняет состояние между подключениями клиента; это не обещание вечного хранения данных.

**Publish acknowledgment** подтверждает прием публикации JetStream. **Consumer Ack** подтверждает обработку
доставки. **Nak** просит повтор, **NakWithDelay** — повтор с задержкой, **InProgress** продлевает ожидание,
**Term** прекращает повторы этой доставки для consumer. При отсутствии ack до истечения таймера возможна
повторная доставка, в том числе другому worker.

В JetStream нет необходимости коммитить Kafka offset. Он хранит stream sequence и состояние подтверждений
consumer. Дедупликация публикаций по `Nats-Msg-Id` действует в заданном окне; подтверждение ack через
DoubleAck уменьшает неопределенность доставки, но не делает внешнюю бизнес-операцию автоматически
exactly-once.

В кластере NATS серверы общаются по routes. JetStream использует Raft для metadata и групп реплик
streams/consumers. При R=3 для работы группы нужны две реплики. Приложение может подключиться к доступному
серверу; внутреннюю маршрутизацию выполняет NATS.

## [Часть I. Теория](#содержание)

<a id="1-core-nats-и-jetstream-зачем-два-уровня"></a>

### [1. Core NATS и JetStream: зачем два уровня](#содержание)

**Core NATS** решает задачу быстрой связи между работающими сейчас приложениями: публикация, подписка,
request/reply и распределение доставок в queue groups.

**JetStream** нужен, когда сообщение должно дождаться обработчика, пережить перезапуск, читаться повторно или
иметь отслеживаемое подтверждение обработки. Он использует NATS как транспорт и добавляет хранение и состояние
доставки.

Один сервер может одновременно обслуживать Core NATS и JetStream. Разница в том, как настроены
subjects/streams и каким API пользуется приложение. Включить JetStream недостаточно: нужно создать stream,
захватывающий нужные subjects.

| Свойство | Core NATS | JetStream |
| --- | --- | --- |
| Сообщение для offline-получателя | Не сохраняется Core NATS | Может храниться в stream |
| История и replay | Нет | Есть, пока данные доступны |
| Обычная модель получения | Push подписчику | Pull или push consumer |
| Подтверждение обработки | Нет | Зависит от AckPolicy, обычно explicit ack |
| Повтор после сбоя обработчика | Не организуется | Возможен по состоянию consumer |
| Базовая семантика | At-most-once | At-least-once при подходящих настройках |

Не каждому сообщению нужна долговечность. Для live-обновлений состояния Core NATS может быть достаточно, а для
сохраняемых событий и задач обычно рассматривают JetStream.

Источники: [Core NATS](https://docs.nats.io/learn/core-nats/) и [модель
JetStream](https://docs.nats.io/concepts/jetstream).

<a id="2-основные-сущности"></a>

### [2. Основные сущности](#содержание)

| Сущность | Что это |
| --- | --- |
| NATS server / node | Процесс nats-server, принимающий подключения и маршрутизирующий сообщения |
| Connection | Долгоживущее сетевое подключение клиента к одному серверу |
| Publisher | Приложение, публикующее сообщения |
| Message | Subject, данные, возможные headers и reply subject |
| Subject | Адрес сообщения и основа маршрутизации |
| Subscription | Подписка клиента на subject или шаблон subjects |
| Queue group | Группа Core-подписок, совместно распределяющих доставки |
| Stream | Серверное хранилище сообщений выбранных subjects |
| JetStream consumer | Серверный объект выбора сообщений и учета доставок/ack |
| Worker / client | Процесс приложения, который получает и обрабатывает доставки |
| Account | Изолированное пространство subjects и ресурсов с собственными правилами доступа |

Consumer в повседневной речи иногда означает приложение-получатель. В JetStream документации это также
конкретный серверный объект. В этом конспекте **consumer** — серверное состояние, а **worker** — экземпляр
Go-приложения, использующий его.

Ни exchange, ни RabbitMQ binding здесь объявлять не требуется. Путь доставки определяется subjects,
подписками, stream configuration и consumer filters.

<a id="3-subjects-wildcards-и-маршрутизация"></a>

### [3. Subjects, wildcards и маршрутизация](#содержание)

**Subject** — регистрозависимая строка, разделенная точками на части. Publisher указывает конкретный subject,
а subscriber может использовать шаблон.

Subject сам по себе не является хранилищем и не имеет настроек retention. Его не нужно предварительно
создавать как topic Kafka. Создаются подписки, streams и consumers, использующие subjects.

| Wildcard | Значение |
| --- | --- |
| `*` | Ровно одна часть subject |
| `>` | Одна или больше частей; используется в конце шаблона |

У `>` есть важное отличие от `#` у RabbitMQ topic exchange: **он не заменяет ноль частей**. Публиковать
следует в конкретный subject, а не в шаблон с wildcards.

Core NATS маршрутизирует по заинтересованным подпискам. Серверы кластера обмениваются информацией об интересе,
чтобы передавать сообщения к подписчикам на других узлах.

Подробнее: [subjects и wildcards](https://docs.nats.io/concepts/subjects).

<a id="4-подписки-queue-groups-и-requestreply"></a>

### [4. Подписки, queue groups и request/reply](#содержание)

<a id="обычная-подписка-и-queue-group"></a>

#### [Обычная подписка и queue group](#содержание)

У обычных подписок каждый подходящий subscriber получает свою доставку. В **queue group** сервер выбирает
одного участника на конкретную доставку. Это позволяет нескольким экземплярам обработчика совместно выполнять
работу.

Обычная Core queue group не является дисковой очередью. Ее имя задается при подписке, а не создает отдельный
backlog для offline workers. Если участник получил сообщение и упал, Core NATS не ждет его ack и не организует
повтор.

Разные queue groups с подходящими подписками получают независимые доставки. Не требуется сопоставлять
количество групп с количеством NATS servers.

Подробнее: [queue groups](https://docs.nats.io/learn/core-nats/queue-groups).

<a id="requestreply"></a>

#### [Request/reply](#содержание)

**Request/reply** — отправка сообщения с адресом для ответа. Клиент создает временный reply subject, часто
называемый **inbox**, публикует запрос и ждет ответ с timeout.

```text
Requester ── запрос + reply subject ──→ Responder
Requester ←── ответ в reply subject ─── Responder
```

Это способ реализовать RPC через NATS, а не отдельная гарантия хранения. Timeout не доказывает, что responder
не выполнил действие: ответ мог потеряться. Для повторных бизнес-команд по-прежнему важны идентификатор
операции и идемпотентность.

**NATS inbox** — subject для ответа. Это не таблица inbox для транзакционной дедупликации, которую мы
обсуждали в конспекте Kafka.

<a id="5-streams-что-сохраняется-и-где"></a>

### [5. Streams: что сохраняется и где](#содержание)

**Stream** — именованное серверное хранилище, которое захватывает публикации с заданных subjects. Publisher
по-прежнему отправляет в subject, а не использует имя stream как адрес назначения.

```text
Subject X ──┐
Subject Y ──┼──→ Stream → сохраненные записи
Subject Z ──┘
```

При сохранении сообщение получает **stream sequence** — номер позиции внутри этого stream. Он не является
глобальным идентификатором для всех streams. Subject и имя stream — разные сущности.

Обычно в одном account subjects обычных streams не должны пересекаться: JetStream отвергает перекрывающий
захват. Для независимого чтения не требуется создавать копию stream на каждый сервис — создают разные
consumers. Для копирования существуют отдельные механизмы mirrors/sources.

<a id="filestorage-и-memorystorage"></a>

#### [FileStorage и MemoryStorage](#содержание)

| Режим | Где находится хранимое состояние |
| --- | --- |
| FileStorage | Файлы на диске узла; RAM используется для буферов, индексов и операций |
| MemoryStorage | Хранилище в памяти; перезапуск процесса теряет его локальные данные |

FileStorage не означает «все байты только на диске». MemoryStorage с репликацией может пережить потерю одной
реплики, но не является заменой дисковому восстановлению после потери всех процессов. Для долговечности
учитывают сохраняемые диски, репликацию и поведение при отказах.

У FileStorage есть собственные правила сброса файлов на диск. Publish ack не следует переводить в утверждение
«каждая запись обязательно fsync-нута на всех физических дисках». Отказ процесса, потеря машины и потеря всех
носителей — разные сценарии.

<a id="ограничения-и-поведение-при-переполнении"></a>

#### [Ограничения и поведение при переполнении](#содержание)

| Настройка | Что ограничивает |
| --- | --- |
| MaxAge | Возраст сообщений |
| MaxMsgs | Количество сообщений |
| MaxBytes | Объем stream |
| MaxMsgsPerSubject | Количество сообщений для отдельного subject |
| MaxMsgSize | Размер отдельного сообщения |
| Replicas | Количество реплик stream, включая leader |

При **DiscardOld** лимиты могут приводить к удалению старых записей. При **DiscardNew** новые публикации,
превышающие соответствующие лимиты объема/количества, отклоняются. Ограничение MaxAge продолжает ограничивать
возраст данных.

Наличие pending ack не отменяет лимиты хранения. Нельзя обещать хранение до успешной обработки при конечных
MaxAge/MaxBytes независимо от нагрузки и политики переполнения.

<a id="6-retention-когда-ack-удаляет-сообщение"></a>

### [6. Retention: когда ack удаляет сообщение](#содержание)

У stream выбирается одна retention policy. Лимиты хранения продолжают иметь значение при любой политике.

| Политика | Основное поведение |
| --- | --- |
| **LimitsPolicy** | Данные хранятся в пределах лимитов; ack consumers не удаляет их сам по себе |
| **InterestPolicy** | Сообщение удерживается, пока заинтересованные consumers не подтвердили его |
| **WorkQueuePolicy** | После успешного ack работы сообщение удаляется |

<a id="limitspolicy"></a>

#### [LimitsPolicy](#содержание)

Подходит для журнала событий и независимых readers. Можно создать новый consumer и прочитать сохраненную
историю. Завершение обработки одним consumer не мешает другому прочитать запись.

<a id="interestpolicy"></a>

#### [InterestPolicy](#содержание)

Учитывает **серверные consumers**, а не только прямо сейчас подключенные Go-процессы. Durable consumer может
сохранять интерес, пока его workers offline.

Если для публикации нет заинтересованного consumer, сообщение не сохраняется для гипотетического будущего
consumer. Добавление новой подписки позже не восстанавливает уже удаленную историю.

<a id="workqueuepolicy"></a>

#### [WorkQueuePolicy](#содержание)

Подходит для распределения задач. Consumers с пересекающимися фильтрами для такого stream не допускаются: одно
сообщение не должно независимо обрабатываться двумя серверными consumers.

Для параллельной обработки несколько workers используют **один consumer**. Можно иметь разные consumers на
непересекающихся subjects, но не два независимых читателя одного и того же задания.

Подробнее: [retention policies](https://docs.nats.io/learn/jetstream/retention-policies).

<a id="7-jetstream-consumers-и-экземпляры-приложения"></a>

### [7. JetStream consumers и экземпляры приложения](#содержание)

**Consumer** задает, какие сообщения stream читать, откуда начинать, как доставлять и как учитывать
подтверждения. Сообщения хранятся в stream, а consumer хранит состояние их выдачи.

```text
                        ┌→ Consumer A → Worker A1
Stream ─────────────────┤             → Worker A2
                        └→ Consumer B → Worker B1
```

A и B — независимые серверные состояния при подходящей retention policy. A1 и A2 совместно выполняют работу A.
Это не три независимых consumer groups только потому, что запущены три процесса.

<a id="durable-и-ephemeral"></a>

#### [Durable и ephemeral](#содержание)

**Durable consumer** имеет устойчивое имя и сохраняет состояние между подключениями workers. Приложение может
получить существующий consumer по имени вместо создания нового при каждом запуске.

**Ephemeral consumer** рассчитан на временное использование и может очищаться сервером после неактивности.
Правила cleanup определяются конфигурацией; InactiveThreshold может применяться и к durable consumer, если
настроен. Ни один вариант не защищен от явного удаления.

Durable относится к жизненному циклу consumer. Это не то же самое, что durable queue RabbitMQ, и не выбор
FileStorage для сообщений: эти настройки задаются отдельно.

<a id="фильтр-и-начальная-позиция"></a>

#### [Фильтр и начальная позиция](#содержание)

**FilterSubject** выбирает сообщения stream по subject. Поддерживаются и несколько FilterSubjects в подходящих
версиях сервера/клиента. Это фильтр чтения, а не создание новой физической очереди с копиями всех сообщений.

**DeliverPolicy** определяет старт: все доступные сообщения, только новые, последняя запись, заданный sequence
или время. После создания durable consumer продолжает по своему состоянию; повторное подключение к нему не
означает новый старт с начала.

**ReplayPolicy** отдельно задает темп replay: как можно быстрее или с учетом исходных интервалов. Начальная
позиция и скорость воспроизведения — разные настройки.

<a id="8-pull-push-и-масштабирование-обработки"></a>

### [8. Pull, push и масштабирование обработки](#содержание)

<a id="pull-consumer"></a>

#### [Pull consumer](#содержание)

Worker запрашивает одну запись или batch, сервер возвращает доступные сообщения по запросу. Библиотека может
непрерывно посылать pull-запросы в фоне, даже если приложение получает callbacks.

Несколько workers могут совместно использовать один durable pull consumer. Для этого не требуется сначала
создавать partitions как в Kafka. Распределяются сообщения общей работы, а не фиксированное число partition
assignments.

<a id="push-consumer"></a>

#### [Push consumer](#содержание)

Сервер доставляет сообщения в настроенный **DeliverSubject**, на который подписывается клиент. Возможна работа
группы с согласованной конфигурацией DeliverGroup и queue-подпиской.

Push тоже требует обработки нагрузки, подтверждений и правил жизненного цикла. Для изучения и обычных
масштабируемых workers дальше используется pull-вариант.

<a id="backpressure-и-порядок"></a>

#### [Backpressure и порядок](#содержание)

**MaxAckPending** ограничивает количество неподтвержденных доставок consumer в целом, включая всех
использующих его workers. Размер batch и локальный параллелизм — другие ограничения. Это близко по цели к
prefetch, но не полностью одинаковая настройка.

У stream есть порядок sequence, но несколько workers могут завершать обработку в другом порядке. Повторные
доставки также меняют наблюдаемый порядок. Одна операция может быть повторно доставлена, пока предыдущий
worker еще работает, если истекло ожидание ack.

Специальный **ordered consumer** помогает последовательно просматривать поток; его не следует автоматически
считать durable worker queue с manual ack и распределением нагрузки.

Подробнее: [pull consumers](https://docs.nats.io/learn/jetstream/pull-consumers).

<a id="9-подтверждения-и-повторная-доставка"></a>

### [9. Подтверждения и повторная доставка](#содержание)

<a id="publish-acknowledgment"></a>

#### [Publish acknowledgment](#содержание)

JetStream publish API может дождаться ответа сервера о сохранении публикации в stream. Ответ содержит stream,
sequence и признак дедупликации. Это не подтверждение бизнес-обработки.

Core Publish в subject, захватываемый stream, тоже может привести к сохранению, но сам Core API не дает такого
подтверждения. **Flush** проверяет обработку предшествующих протокольных команд сервером, а не успешную
обработку consumers и не заменяет JetStream publish ack.

Если ответ на публикацию потерялся, результат для publisher неопределен. Повторять публикацию нужно с учетом
возможности дубля и выбранного message ID.

<a id="consumer-acknowledgments"></a>

#### [Consumer acknowledgments](#содержание)

| Ответ | Смысл |
| --- | --- |
| **Ack** | Обработка завершена, доставка подтверждена |
| **DoubleAck** | Отправить ack и дождаться подтверждения его приема сервером |
| **Nak** | Запросить повторную доставку без ожидания обычного ack timeout |
| **NakWithDelay** | Запросить повтор с заданной задержкой |
| **InProgress** | Сообщить о продолжающейся работе и продлить ожидание ack |
| **Term** | Прекратить дальнейшие попытки для этого сообщения у данного consumer |

DoubleAck не выполняет бизнес-операцию дважды: название относится к подтверждению самого ack. Ошибочный
результат ожидания не доказывает, что ack не был принят.

**AckExplicit** требует отдельного подтверждения каждой доставки. **AckAll** подтверждает диапазон и требует
осторожности при совместной/параллельной обработке. **AckNone** не ожидает явных подтверждений от приложения.
В примерах используется AckExplicit.

<a id="ackwait-backoff-и-maxdeliver"></a>

#### [AckWait, BackOff и MaxDeliver](#содержание)

**AckWait** — сколько ждать ack перед повтором. **BackOff** может задать последовательность ожиданий повторной
доставки вместо одного AckWait. Обычный Nak не обязан ждать этот BackOff: для явной задержки используется
NakWithDelay.

**MaxDeliver** ограничивает число попыток доставки. После достижения лимита не возникает автоматическая DLQ,
как будто в stream включен RabbitMQ DLX. JetStream публикует advisory; реакцию и перенос в отдельный
stream/subject организует приложение или инфраструктура.

Term также не является командой «перенеси в DLQ». Судьба записи в stream зависит от retention. При
LimitsPolicy запись может оставаться доступной, хотя этот consumer больше ее не повторяет.

Отсутствие ack и новый подключившийся worker не всегда означают немедленный повтор: сервер руководствуется
таймерами и состоянием consumer, а не просто фактом разрыва соединения.

<a id="10-sequence-ack-floor-и-отличие-от-kafka-commit"></a>

### [10. Sequence, ack floor и отличие от Kafka commit](#содержание)

У JetStream есть несколько счетчиков, которые нельзя смешивать:

| Значение | Что описывает |
| --- | --- |
| Stream sequence | Позиция сохраненной записи в stream |
| Consumer sequence | Последовательность доставок consumer, включая повторные |
| Ack floor | Граница состояния подтвержденных доставок consumer |
| NumPending | Данные, еще ожидающие выдачи consumer согласно его состоянию |
| NumAckPending | Выданные сообщения, для которых ожидается ack |
| NumRedelivered | Состояние/счетчик повторных доставок, показываемый consumer info |

Повторно доставленная запись сохраняет stream sequence, но получает новую позицию доставки в consumer
sequence. Из-за удаления сообщений, фильтрации и повторов эти номера не обязаны совпадать.

При AckExplicit сервер может отслеживать отдельные подтверждения с пропусками. Ack более поздней доставки не
равнозначен Kafka commit, который автоматически продвигает позицию поверх предыдущих offsets этой partition.
Здесь не нужно вручную выставлять «следующий offset» после Ack.

Metadata сообщения полезна для диагностики, но бизнес-идентификатор события лучше передавать явно. Sequence
привязан к конкретному stream и не заменяет идентификатор логической операции.

<a id="11-дедупликация-и-границы-exactly-once"></a>

### [11. Дедупликация и границы exactly-once](#содержание)

JetStream может подавлять повторные публикации по заголовку **Nats-Msg-Id** в течение **duplicate window**
stream. В Go этому соответствует опция WithMsgID.

Если publisher не получил ответ и повторяет ту же логическую публикацию, он использует тот же ID. Новый
бизнес-event получает новый ID. Сравнивается идентификатор, а не JSON payload.

После окончания окна повтор может снова сохраниться. Если два разных события ошибочно имеют один ID, второе
может быть подавлено. Большое окно также требует ресурсов.

Дедупликация публикаций и подтвержденный ack используются в описаниях exactly-once возможностей JetStream, но
их нельзя переводить в обещание единственного эффекта во внешней БД:

```text
Worker изменил PostgreSQL → упал до ack → возможна повторная доставка.
```

Для списания денег, изменения остатков и других эффектов нужны подходящие транзакции, идемпотентность и
согласованный протокол. Ни DoubleAck, ни Nats-Msg-Id не включают PostgreSQL в общую транзакцию автоматически.

<a id="12-подключения-и-кластеризация"></a>

### [12. Подключения и кластеризация](#содержание)

<a id="connection-и-маршруты-между-серверами"></a>

#### [Connection и маршруты между серверами](#содержание)

Клиент обычно держит connection к одному NATS server. Через него идут разные публикации, подписки и
JetStream-запросы. AMQP channels для этого не открываются.

Серверы объединяются в cluster и обмениваются сообщениями по **routes**. Приложения могут публиковать и
получать данные через разные узлы. Клиенту не нужно находиться на одной машине со stream leader.

```text
Go publisher → NATS A ── route ──→ NATS B ←── route ──→ NATS C ← Go worker
```

Доставка к нужному объекту происходит внутри NATS. В отличие от Kafka, приложение не строит прямые соединения
с leaders каждой partition для обычной публикации.

<a id="jetstream-replication-и-лидеры"></a>

#### [JetStream replication и лидеры](#содержание)

У JetStream есть metadata Raft group и группы реплик streams/consumers. Leader stream и leader метаданных —
разные роли. Состояние consumer также имеет репликацию; по умолчанию ее настройки связаны с репликацией stream
и могут конфигурироваться отдельно.

| Replicas stream | Что означает |
| --- | --- |
| 1 | Одна копия, нет переключения на другую replica stream при отказе этого узла |
| 3 | Три копии, большинство — две; допустим отказ одной replica |

Три servers в cluster не превращают каждый stream автоматически в R=3. Число replicas задают для stream и
проверяют его размещение. Добавление узла не означает само по себе трехкратный рост производительности одного
stream.

В отличие от привычной модели Kafka, у stream нет обязательного набора пользовательских partitions, число
которых равно пределу workers. Это не означает неограниченной пропускной способности: leader, диски, сеть и
состояние consumer по-прежнему имеют ограничения. Для разделения потоков проектируют несколько
streams/subjects и подходящую топологию.

<a id="отказ-узла-и-reconnect"></a>

#### [Отказ узла и reconnect](#содержание)

При R=3 оставшееся большинство может выбрать нового leader. Одновременно приложение, подключенное к упавшему
серверу, теряет свое connection и должно переподключиться.

NATS-клиенты поддерживают reconnect и могут узнавать адреса других servers. Начальные адреса и advertised
addresses должны быть достижимы. Reconnect не возвращает потерянные Core-сообщения, а восстановление
бизнес-операции остается задачей приложения.

Для Core NATS нет единственного главного узла, через который обязательно идет вся маршрутизация. У JetStream
лидерство относится к конкретным реплицируемым состояниям.

Подробнее: [JetStream в кластере](https://docs.nats.io/learn/topologies/jetstream-in-a-cluster).

<a id="13-мониторинг-ограничения-и-выбор-технологии"></a>

### [13. Мониторинг, ограничения и выбор технологии](#содержание)

Нужно наблюдать состояние stream, consumer и приложения отдельно:

- размер stream, возраст сообщений, заполнение лимитов и ошибки публикаций;

- Pending, AckPending, Redelivered и достижение MaxDeliver;

- доступность replicas и наличие leaders;

- время бизнес-обработки относительно AckWait;

- slow consumers, ошибки подписок, reconnect и нагрузку на сеть/диск;

- успехи и ошибки бизнес-операций, а не только сообщения «доставлено».

Slow consumer в Core NATS не означает, что сервер создаст ему надежную дисковую очередь: срабатывают
ограничения и механизмы обнаружения перегрузки.

| Требование | Что рассматривать |
| --- | --- |
| Быстрая связь работающих сейчас сервисов, request/reply | Core NATS |
| Задания с подтверждениями, хранение и replay внутри NATS | JetStream с подходящими consumers/retention |
| Сохраненный partitioned log и независимые группы обработки | Kafka |
| Exchange-маршрутизация и обычные очереди задач | RabbitMQ |

Это ориентиры, а не жесткие запреты. Для JetStream важно заранее выбрать retention: одна и та же технология
может работать ближе к журналу событий или к очереди задач.

<a id="часть-ii-примеры-настройки-и-использования"></a>

## [Часть II. Примеры настройки и использования](#содержание)

В примерах используются `orders` и `feed`, как в предыдущих конспектах. Сначала показано поведение, затем
локальный запуск и код. Теоретические определения выше не зависят от этого кейса.

<a id="пример-subjects-и-wildcards"></a>

### [Пример: subjects и wildcards](#содержание)

| Подписка или фильтр | orders.created | orders.eu.created | orders | posts.created |
| --- | --- | --- | --- | --- |
| orders.created | Да | Нет | Нет | Нет |
| orders.* | Да | Нет | Нет | Нет |
| orders.> | Да | Да | Нет | Нет |
| *.created | Да | Нет | Нет | Да |

`orders.>` не включает точный subject `orders`. Если он тоже нужен, это учитывают отдельной
подпиской/конфигурацией, а не переносят поведение RabbitMQ `orders.#`.

<a id="пример-core-nats-и-две-копии-обработчика"></a>

### [Пример: Core NATS и две копии обработчика](#содержание)

Publisher отправляет в `orders.created`:

```json
{"event_id":"event-123","order_id":"order-42","type":"OrderCreated"}
```

Если все три workers используют обычные subscriptions:

```text
orders.created ──┬──→ orders-worker-1
                ├──→ orders-worker-2
                └──→ feed-worker-1
```

Все подходящие подписки получают сообщение. Это приведет к двум обработкам заказа, если orders-worker-1 и
orders-worker-2 делают одно и то же.

Для разделения работы используем две queue groups:

```text
orders.created ──┬──→ queue group orders ──→ worker 1 ИЛИ worker 2
                └──→ queue group feed   ──→ worker F
```

Worker F независимо обновляет ленту, а один из orders workers обрабатывает заказ. Если все orders workers
offline и нет stream, сохраняющего публикацию, позже они это сообщение из Core NATS не получат. Само имя queue
group не создает backlog.

<a id="пример-jetstream-и-независимые-ordersfeed"></a>

### [Пример: JetStream и независимые orders/feed](#содержание)

Создаем один stream **SHOP_EVENTS**:

```text
subjects: orders.>, posts.>
storage: file
retention: limits
```

Создаем два durable pull consumers:

| Consumer | Фильтр | Назначение |
| --- | --- | --- |
| ORDERS_WORKERS | orders.> | Обработка событий заказов |
| FEED_WORKERS | orders.created, posts.created | Обновление ленты при создании заказа/поста |

```text
Publisher → orders.created → SHOP_EVENTS
                                  │
                  ┌───────────────┴────────────────┐
                  ▼                                ▼
             ORDERS_WORKERS                    FEED_WORKERS
               /       \                            │
          worker A    worker B                   worker F
```

У A и B один серверный consumer. Они делят его сообщения, не получая независимую копию на каждый процесс. У F
другой consumer с собственным состоянием.

Ack от ORDERS_WORKERS не подтверждает обработку у FEED_WORKERS. При LimitsPolicy запись остается в stream
после обоих ack до удаления по лимитам или явного управления.

Если FEED_WORKERS временно не обслуживается workers, его можно продолжить позже, пока сохранились данные.
Новый consumer также может прочитать доступную историю при DeliverAll. Для этого не создают второй stream с
теми же subjects.

<a id="пример-как-меняется-retention"></a>

### [Пример: как меняется retention](#содержание)

Публикуем одно событие, а два независимых consumers хотят его прочитать:

| Политика stream | Что происходит |
| --- | --- |
| Limits | Оба могут обработать запись; ack не удаляет ее из stream |
| Interest | Запись нужна, пока оба заинтересованных consumers не подтвердили ее; дополнительно действуют лимиты |
| WorkQueue | Два consumers с пересекающимся интересом создать нельзя |

Если нужны **два разных бизнес-эффекта** — обработать заказ и обновить ленту — WorkQueue нельзя просто
включить в прежней схеме, сохранив пересекающиеся filters.

Если нужна **одна задача, выполненная одним из пяти workers**, можно использовать WorkQueue с одним durable
pull consumer и пятью приложениями, которые его разделяют.

<a id="пример-ack-timeout-и-повторная-доставка"></a>

### [Пример: ack, timeout и повторная доставка](#содержание)

```text
Stream sequence 42 → Consumer ORDERS_WORKERS → Worker A
                         AckWait = 30 seconds
```

1. A начал работу, но за 30 секунд ack не получен.

2. Consumer может повторно выдать stream sequence 42 worker B. A при этом не обязательно умер:
   он мог долго выполнять запрос в БД.

3. B выполняет операцию и отправляет Ack или DoubleAck.

4. Судьба записи в stream определяется retention. При LimitsPolicy она остается, но ORDERS_WORKERS
   считает доставку подтвержденной.

Поэтому ack timeout не является распределенной блокировкой бизнес-операции. Для долгой обработки выбирают
подходящий AckWait и отправляют InProgress, а от дублей защищают бизнес-логику.

<a id="пример-запуск-локального-nats-с-jetstream"></a>

### [Пример: запуск локального NATS с JetStream](#содержание)

`nats-server` — сервер, `nats` — отдельная CLI-утилита. Наличие одной не означает установки другой.

Если сервер уже установлен:

```bash
nats-server -js -sd /tmp/nats-notes-data
```

Для повторных запусков сохраняем тот же store directory. Каталог `/tmp` удобен для учебы, но может очищаться
системой; это не постоянное production-хранилище.

Вариант `compose.yml`:

```yaml
services:
  nats:
    image: nats:2.11
    command: ["-js", "-sd", "/data", "-m", "8222"]
    ports:
      - "4222:4222"
      - "127.0.0.1:8222:8222"
    volumes:
      - nats-data:/data

volumes:
  nats-data:
```

```bash
docker compose up -d
```

4222 — клиентский порт, 8222 — monitoring HTTP. В этом учебном Compose volume сохраняет данные при обычном
пересоздании контейнера. Удаление самого volume уничтожит и данные.

Monitoring interface не является системой управления доступом; в примере он доступен только на loopback хоста.
Аутентификация, TLS и permissions на subjects/JetStream API настраиваются отдельно при эксплуатации за
пределами локального примера.

<a id="пример-jetstream-cluster-на-трех-машинах"></a>

### [Пример: JetStream cluster на трех машинах](#содержание)

Три Linux-машины имеют собственные диски и разрешают имена друг друга:

| Имя | IP | Клиенты | Routes |
| --- | --- | --- | --- |
| n1 | 10.0.0.31 | 4222 | 6222 |
| n2 | 10.0.0.32 | 4222 | 6222 |
| n3 | 10.0.0.33 | 4222 | 6222 |

<a id="конфигурация-nats-server"></a>

#### [Конфигурация nats-server](#содержание)

Пример файла `nats.conf` для n1 в учебной частной сети:

```text
server_name: n1
port: 4222

jetstream {
  store_dir: "/var/lib/nats/jetstream"
  max_memory_store: 256MB
  max_file_store: 10GB
}

cluster {
  name: shop
  listen: "0.0.0.0:6222"
  routes: [
    nats://10.0.0.32:6222
    nats://10.0.0.33:6222
  ]
}
```

У n2 и n3 меняют server_name и список routes на другие два узла. Cluster name `shop` одинаковый, каталог
store_dir у каждого свой локальный. Пользователь сервера должен иметь доступ к каталогу. Между серверами
разрешают 6222, приложениям — 4222. В конфиге специально не показана production-защита: аутентификация
clients/routes и TLS — отдельная настройка.

```bash
nats-server -t -c nats.conf
nats-server -c nats.conf
```

Первая команда проверяет конфиг, вторая запускает сервер. Реальные процессы обычно управляются systemd или
оркестратором. Само совпадение имени cluster не заменяет доступность routes.

<a id="создание-реплицируемого-stream-и-подключение-приложений"></a>

#### [Создание реплицируемого stream и подключение приложений](#содержание)

После объединения трех JetStream-узлов создают stream с **Replicas=3**, а не оставляют локальное R=1. В
Go-примере ниже для этого меняют Replicas при подготовке соответствующего stream.

```text
                      n1            n2            n3
SHOP_EVENTS           Follower      Leader        Follower

Worker A → n1
Worker B → n3     оба используют ORDERS_WORKERS
Worker F → n2     использует FEED_WORKERS
```

Клиентам можно передать несколько адресов:

```text
nats://10.0.0.31:4222,nats://10.0.0.32:4222,nats://10.0.0.33:4222
```

Это список для выбора подключения и reconnect, а не три независимых публикации. Приложение не должно
отправлять каждое событие по одному разу на каждый сервер.

Если n2 недоступен, большинство из n1/n3 может выбрать нового leader stream. Приложение, подключенное к n2,
отдельно восстанавливает connection. Повторное подключение не отменяет неопределенность publish/ack на границе
сбоя.

<a id="go-подключение-stream-consumers-publish-и-ack"></a>

### [Go: подключение, stream, consumers, publish и ack](#содержание)

В примере используется **nats.go v1.47.0**, пакет `github.com/nats-io/nats.go/jetstream`. Это современный
JetStream API выбранной версии. В старых примерах встречается `nc.JetStream()` и другой набор методов — не
нужно смешивать оба API в одной шпаргалке.

<a id="что-создается-в-go-и-на-сервере"></a>

#### [Что создается в Go и на сервере](#содержание)

| Вызов | Результат |
| --- | --- |
| nats.Connect | Подключение к NATS server |
| jetstream.New | Клиентский JetStream API поверх connection; не включает JetStream на сервере |
| CreateOrUpdateStream | Создать/согласовать серверную конфигурацию stream |
| CreateOrUpdateConsumer | Создать/согласовать consumer и его состояние на сервере |
| js.Consumer | Получить объект для работы с уже существующим consumer |
| js.Publish | Публикация с ожиданием JetStream publish ack |
| consumer.Next | Запросить следующее сообщение pull consumer |
| msg.DoubleAck | Подтвердить обработку и дождаться ответа на ack |

CreateOrUpdate не означает, что любые поля можно произвольно менять у существующего объекта. Часть изменений
ограничена сервером; ошибка возвращается приложению. В реальной системе топологией может управлять отдельный
deployment/admin-процесс с соответствующими правами.

<a id="полный-учебный-пример"></a>

#### [Полный учебный пример](#содержание)

Один `main.go` имеет режимы init, produce и consume. Создание topology отделено от чтения. Используется
LimitsPolicy, чтобы ORDERS_WORKERS и FEED_WORKERS могли независимо читать сохраненные события.

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"log"
	"os"
	"os/signal"
	"syscall"
	"time"

	"github.com/nats-io/nats.go"
	"github.com/nats-io/nats.go/jetstream"
)

const streamName = "SHOP_EVENTS"

type Event struct {
	EventID string `json:"event_id"`
	OrderID string `json:"order_id"`
	Type    string `json:"type"`
}

func setup(ctx context.Context, js jetstream.JetStream) error {
	_, err := js.CreateOrUpdateStream(ctx, jetstream.StreamConfig{
		Name:       streamName,
		Subjects:   []string{"orders.>", "posts.>"},
		Storage:    jetstream.FileStorage,
		Retention:  jetstream.LimitsPolicy,
		Discard:    jetstream.DiscardOld,
		Replicas:   1, // Локальный сервер; для кластера из трех узлов можно выбрать 3.
		MaxAge:     24 * time.Hour,
		MaxMsgs:    10000,
		MaxBytes:   64 * 1024 * 1024,
		Duplicates: 2 * time.Minute,
	})
	if err != nil {
		return fmt.Errorf("stream: %w", err)
	}

	for _, cfg := range []jetstream.ConsumerConfig{
		{
			Durable:       "ORDERS_WORKERS",
			FilterSubject: "orders.>",
			AckPolicy:     jetstream.AckExplicitPolicy,
			DeliverPolicy: jetstream.DeliverAllPolicy,
			AckWait:       30 * time.Second,
			MaxDeliver:    5,
			MaxAckPending: 100,
		},
		{
			Durable:        "FEED_WORKERS",
			FilterSubjects: []string{"orders.created", "posts.created"},
			AckPolicy:      jetstream.AckExplicitPolicy,
			DeliverPolicy:  jetstream.DeliverAllPolicy,
			AckWait:        30 * time.Second,
			MaxDeliver:     5,
			MaxAckPending:  100,
		},
	} {
		if _, err := js.CreateOrUpdateConsumer(ctx, streamName, cfg); err != nil {
			return fmt.Errorf("consumer %s: %w", cfg.Durable, err)
		}
	}
	return nil
}

func publish(ctx context.Context, js jetstream.JetStream, event Event) error {
	payload, err := json.Marshal(event)
	if err != nil {
		return err
	}
	ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()

	ack, err := js.Publish(ctx, "orders.created", payload, jetstream.WithMsgID(event.EventID))
	if err != nil {
		return fmt.Errorf("publish: %w", err)
	}
	log.Printf("stored: stream=%s sequence=%d duplicate=%t", ack.Stream, ack.Sequence, ack.Duplicate)
	return nil
}

func handle(ctx context.Context, msg jetstream.Msg) error {
	if err := ctx.Err(); err != nil {
		return err
	}
	var event Event
	if err := json.Unmarshal(msg.Data(), &event); err != nil {
		return err
	}
	if event.EventID == "" || event.OrderID == "" {
		return errors.New("event_id and order_id are required")
	}
	// Здесь выполняется бизнес-операция; пока только выводим событие.
	log.Printf("subject=%s event=%s order=%s", msg.Subject(), event.EventID, event.OrderID)
	return nil
}

func consume(ctx context.Context, js jetstream.JetStream, name string) error {
	lookupCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
	consumer, err := js.Consumer(lookupCtx, streamName, name)
	cancel()
	if err != nil {
		return fmt.Errorf("lookup consumer: %w", err)
	}

	for ctx.Err() == nil {
		msg, err := consumer.Next(jetstream.FetchMaxWait(time.Second))
		if errors.Is(err, nats.ErrTimeout) {
			continue
		}
		if err != nil {
			return fmt.Errorf("next: %w", err)
		}

		if err := handle(ctx, msg); err != nil {
			log.Printf("handle failed: %v", err)
			if nakErr := msg.NakWithDelay(2 * time.Second); nakErr != nil {
				return fmt.Errorf("nak: %w", nakErr)
			}
			continue
		}

		ackCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
		ackErr := msg.DoubleAck(ackCtx)
		cancel()
		if ackErr != nil {
			return fmt.Errorf("ack result uncertain: %w", ackErr)
		}
	}
	return nil
}

func run(ctx context.Context, args []string) (err error) {
	nc, err := nats.Connect(nats.DefaultURL,
		nats.Name("nats-notes"),
		nats.Timeout(5*time.Second),
		nats.MaxReconnects(10),
		nats.ReconnectWait(time.Second),
	)
	if err != nil {
		return err
	}
	defer nc.Close()

	js, err := jetstream.New(nc)
	if err != nil {
		return err
	}
	switch args[0] {
	case "init":
		ctx, cancel := context.WithTimeout(ctx, 10*time.Second)
		defer cancel()
		return setup(ctx, js)
	case "produce":
		eventID := "event-123"
		if len(args) > 1 {
			eventID = args[1]
		}
		return publish(ctx, js, Event{EventID: eventID, OrderID: "order-42", Type: "OrderCreated"})
	case "consume":
		name := "ORDERS_WORKERS"
		if len(args) > 1 {
			name = args[1]
		}
		return consume(ctx, js, name)
	default:
		return fmt.Errorf("unknown mode %q", args[0])
	}
}

func main() {
	if len(os.Args) < 2 {
		log.Print("usage: go run . init|produce [event-id]|consume [consumer-name]")
		return
	}
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	if err := run(ctx, os.Args[1:]); err != nil {
		log.Printf("NATS example stopped: %v", err)
		os.Exit(1)
	}
}
```

<a id="запуск-и-наблюдение"></a>

#### [Запуск и наблюдение](#содержание)

Сохраняем код в `main.go` отдельного каталога, предварительно запустив локальный сервер с JetStream:

```bash
go mod init nats-note-example
go get github.com/nats-io/nats.go@v1.47.0
go run . init
go run . produce event-123
```

В разных терминалах:

```bash
go run . consume ORDERS_WORKERS
go run . consume ORDERS_WORKERS
go run . consume FEED_WORKERS
```

Два первых процесса делят deliveries ORDERS_WORKERS, а третий независимо выполняет работу FEED_WORKERS. Для
нового события выполняем `go run . produce event-124`.

Если установлена NATS CLI, можно посмотреть серверное состояние:

```bash
nats stream info SHOP_EVENTS
nats consumer info SHOP_EVENTS ORDERS_WORKERS
nats consumer info SHOP_EVENTS FEED_WORKERS
```

Файл хранит stream на одном локальном сервере. Для кластера меняют connection URL и Replicas, учитывая
подготовленную topology. Не нужно создавать отдельный SHOP_EVENTS на каждый worker.

<a id="что-важно-заметить-в-коде"></a>

#### [Что важно заметить в коде](#содержание)

- В publish указан subject `orders.created`, а не имя stream SHOP_EVENTS.

- `WithMsgID(event.EventID)` используется для повторов одной логической публикации. Повторная
  отправка event-123 в пределах Duplicates может вернуть duplicate=true без новой записи.

- Publish ack возвращает stream sequence, а не результат обработки orders/feed.

- В этой версии API Next блокируется до сообщения или timeout. Короткий FetchMaxWait позволяет
  периодически проверять отмену контекста. Это pull, даже если чтение происходит в цикле.

- DoubleAck вызывается после handle. В этой функции нет `CommitMessages` и ручного прибавления
  единицы к sequence: сервер сам учитывает подтверждение.

- При ошибке handle отправляется NakWithDelay, и consumer может повторить сообщение. Такой
  `continue` не равен опасному Kafka commit поверх необработанного offset: используется AckExplicit.

- Пример для простоты повторяет и ошибки JSON. В реальном сервисе постоянные ошибки отделяют
  от временных и выбирают Term/DLQ/ручной разбор. MaxDeliver=5 ограничивает попытки, но не создает DLQ.

- В этой функции AckWait=30 секунд. Долгую бизнес-операцию нужно согласовать с этим временем
  или продлевать через InProgress; добавление goroutines не решает истечение ack timeout.

<a id="дополнительные-ответы-на-доставку"></a>

#### [Дополнительные ответы на доставку](#содержание)

В API `jetstream.Msg` доступны методы:

```text
msg.Ack()                         обычное подтверждение
msg.DoubleAck(ctx)                подтверждение с ожиданием ответа сервера
msg.Nak()                         запрос быстрого повтора
msg.NakWithDelay(2 * time.Second)  запрос повтора с задержкой
msg.InProgress()                  продлить ожидание подтверждения
msg.Term()                        прекратить повторы для consumer
```

Ошибки этих методов нужно обрабатывать. При неопределенном результате DoubleAck безопаснее рассчитывать на
возможность повтора, чем объявлять операцию точно не выполненной. Term не публикует запись в отдельный DLQ
stream автоматически.

<a id="connection-flush-drain-и-reconnect"></a>

#### [Connection, Flush, Drain и reconnect](#содержание)

Через одно `*nats.Conn` можно работать с Core NATS и JetStream. Например, Core-подписки создаются методами
Subscribe и QueueSubscribe, публикация — Publish, запрос с ответом — RequestWithContext. У этих Core-сообщений
нет JetStream ack, если приложение работает только с Core API.

**Close** закрывает connection. **Drain** предназначен для аккуратного завершения подписок и исходящих
операций, но его нужно вызывать в правильный момент жизненного цикла приложения. **Flush** не ждет завершения
произвольной бизнес-обработки subscribers.

В полном примере используется базовая отмена контекста и Close после завершения последовательной работы. Это
не готовый production graceful shutdown: полноценный draining, ожидание in-flight операций, retries с jitter и
DLQ остаются отдельной практикой.

Источники Go API: [nats.go v1.47.0](https://pkg.go.dev/github.com/nats-io/nats.go@v1.47.0) и [JetStream
API](https://pkg.go.dev/github.com/nats-io/nats.go@v1.47.0/jetstream).

<a id="краткое-сравнение-с-уже-знакомыми-моделями"></a>

## [Краткое сравнение с уже знакомыми моделями](#содержание)

| Понятие | RabbitMQ | Kafka | NATS / JetStream |
| --- | --- | --- | --- |
| Адрес публикации | Exchange + routing key | Topic и выбранная partition | Subject |
| Хранилище | Queue или специальный stream | Partition logs topic | JetStream stream |
| Независимое чтение | Обычно отдельная queue | Consumer group | Отдельный JetStream consumer при подходящей retention |
| Совместная работа копий | Consumers одной queue | Consumers группы делят partitions | Workers разделяют pull consumer; в Core — queue group |
| Успех обработки | Ack доставки | Commit следующего offset | Ack доставки consumer |
| Неуспех | Nack/requeue/DLX | Прикладной retry и управление позицией | Nak, задержка, timeout, Term; DLQ отдельно |
| Удаление после успеха | Обычно да для обычной queue | Нет, cleanup отдельно | Зависит от retention policy |
| Где выбирается лидер данных | Брокер/реплики queue | Controller назначает leader partition | Raft группы stream |

Не следует механически называть NATS subject «очередью», JetStream consumer «процессом» или Core queue group
«durable consumer». Эти понятия помогают решать похожие задачи, но имеют разное состояние и жизненный цикл.
