<a id="processes-and-threads"></a>
## Программа, процесс и поток

### Программа

**Программа** — исполняемый файл с кодом и данными, который лежит на диске.

Например:

```text
./server
```

Пока файл не запущен, это просто программа.

### Процесс

**Процесс** — запущенный экземпляр программы вместе с выделенным ему окружением.

При запуске программы операционная система:

1. создаёт процесс;
2. выдаёт ему PID;
3. создаёт виртуальное адресное пространство;
4. загружает код и данные в память;
5. создаёт как минимум один поток;
6. начинает выполнять инструкции.

```text
Программа на диске
        ↓ запуск
Процесс в памяти
```

Один бинарник можно запустить несколько раз:

```text
server, PID 1001
server, PID 1002
server, PID 1003
```

Это три независимых процесса.

У процесса есть:

- PID;
- виртуальная память;
- код программы;
- heap;
- один или несколько потоков;
- открытые файлы;
- сетевые сокеты;
- переменные окружения;
- права пользователя;
- рабочая директория.

### Поток

**Поток — отдельная последовательность выполнения инструкций внутри процесса.**

```text
Процесс
├── поток 1
├── поток 2
└── поток 3
```

Процесс является контейнером ресурсов, а потоки непосредственно выполняют код.

### Главное отличие

```text
Процесс — изолированное окружение выполняемой программы.

Поток — исполнитель кода внутри процесса.
```

<a id="memory-and-resources"></a>
## Память и ресурсы процессов и потоков

### Между разными процессами

Разные процессы обычно имеют отдельные виртуальные адресные пространства:

```text
Процесс A              Процесс B
├── heap A              ├── heap B
├── stack потоков A     ├── stack потоков B
└── свои ресурсы        └── свои ресурсы
```

Один процесс не может напрямую читать или изменять память другого процесса.

Для обмена данными используют IPC:

- сетевые сокеты;
- Unix-сокеты;
- pipes;
- shared memory;
- файлы;
- очереди сообщений;
- сигналы.

### Между потоками одного процесса

Потоки одного процесса **разделяют**:

- код программы;
- виртуальное адресное пространство;
- heap;
- глобальные переменные;
- открытые файлы;
- сокеты;
- права и окружение процесса.

У каждого потока **свои**:

- stack;
- регистры CPU;
- указатель текущей инструкции;
- идентификатор потока;
- состояние выполнения.

```text
Процесс
├── общий код
├── общий heap
├── общие файлы и сокеты
│
├── поток 1
│   └── собственный stack
│
└── поток 2
    └── собственный stack
```

Из-за общей памяти потоки могут получить **data race**:

```text
Поток 1 изменяет x
Поток 2 одновременно изменяет x
```

Для синхронизации используют:

- mutex;
- atomic;
- semaphore;
- condition variable;
- каналы в Go.

### Таблица

| Ресурс | Разные процессы | Потоки одного процесса |
|---|---|---|
| Виртуальная память | Обычно отдельная | Общая |
| Heap | Отдельный | Общий |
| Stack | Свой у каждого потока | Свой у каждого потока |
| Код программы | Логически отдельное отображение | Общий |
| Глобальные переменные | Отдельные | Общие |
| Открытые файлы | Принадлежат процессу | Используются совместно |
| Сокеты | Принадлежат процессу | Используются совместно |
| Обмен данными | Через IPC | Через общую память |
| Изоляция | Сильнее | Слабее |

### Go: горутина и поток

Горутина не равна системному потоку.

```text
Много горутин
      ↓
планировщик Go
      ↓
несколько системных потоков
      ↓
планировщик ОС
      ↓
CPU
```

ОС планирует системные потоки. Горутины распределяет Go runtime.

<a id="cpu-scheduling"></a>
## Планирование CPU

Процессорное время фактически получают **потоки**.

Допустим:

```text
4 ядра CPU
6 готовых к выполнению потоков
```

В один момент выполняются примерно четыре потока:

```text
CPU 1 → поток A
CPU 2 → поток B
CPU 3 → поток C
CPU 4 → поток D

Потоки E и F ждут
```

Через небольшой промежуток ОС переключает потоки:

```text
CPU 1 → поток E
CPU 2 → поток B
CPU 3 → поток F
CPU 4 → поток A
```

Это называется **планированием**.

При переключении контекста ОС сохраняет состояние одного потока и восстанавливает состояние другого:

- регистры;
- указатель инструкции;
- указатель stack;
- состояние планировщика.

Процесс или виртуальная машина обычно не забирают конкретное физическое ядро навсегда. Они получают процессорное время. Жёсткое закрепление за ядрами настраивается отдельно.

<a id="namespaces-and-cgroups"></a>
## Namespaces и cgroups

Контейнер создаётся не одним механизмом, а комбинацией механизмов Linux.

### Namespaces

**Namespace определяет, что процесс видит.**

Основные namespaces:

| Namespace | Что изолирует |
|---|---|
| PID | процессы |
| NET | сеть и сетевые интерфейсы |
| MNT | файловую систему и точки монтирования |
| UTS | hostname |
| IPC | межпроцессное взаимодействие |
| USER | пользователей и UID |

Например, благодаря PID namespace процесс внутри контейнера может видеть себя как PID 1, хотя на хосте его PID другой.

### Cgroup

**Cgroup, control group — механизм Linux для учёта и ограничения ресурсов группы процессов.**

Cgroup позволяет ограничивать:

- CPU;
- RAM;
- количество процессов и потоков;
- дисковый I/O;
- относительный приоритет ресурсов.

```text
cgroup контейнера
├── основной процесс
├── дочерние процессы
└── системные потоки
```

Лимит применяется к сумме ресурсов всей группы.

Например:

```bash
docker run --cpus=2 --memory=1g --pids-limit=100 my-app
```

Означает:

- не более вычислительной мощности примерно двух CPU;
- не более 1 ГБ RAM;
- не более 100 процессов и потоков.

Важно:

```text
Namespaces → что процессы видят.

Cgroups → сколько ресурсов процессы могут использовать.
```

Контейнер:

```text
обычные Linux-процессы
+ namespaces
+ cgroups
+ отдельное представление файловой системы
+ ограничения безопасности
```

<a id="virtualization"></a>
## Виртуализация

**Виртуализация — запуск виртуального компьютера с собственной операционной системой и собственным ядром.**

```text
Физический сервер
└── гипервизор
    ├── VM 1
    │   ├── Guest OS
    │   ├── собственное ядро
    │   └── приложения
    │
    └── VM 2
        ├── Guest OS
        ├── собственное ядро
        └── приложения
```

### Гипервизор

Гипервизор создаёт виртуальное оборудование и распределяет физические ресурсы между виртуальными машинами.

Примеры:

- KVM;
- VMware;
- Hyper-V;
- VirtualBox;
- QEMU.

### CPU виртуальной машины

Виртуальной машине задают число **vCPU**:

```text
VM: 4 vCPU
```

Это не обязательно четыре навсегда занятых физических ядра.

Гостевая ОС видит четыре виртуальных CPU, а гипервизор распределяет их выполнение по физическим ядрам.

```text
Приложение в VM
      ↓
планировщик Guest OS
      ↓
vCPU
      ↓
гипервизор
      ↓
физические CPU
```

Можно выделить больше vCPU, чем есть физических CPU. Это называется **overcommit**. Пока не все VM нагружают CPU одновременно, система может работать нормально.

### RAM виртуальной машины

Если VM настроена на 8 ГБ RAM, гостевая ОС видит 8 ГБ виртуальной памяти.

Физические страницы могут выделяться постепенно, но гипервизор должен обеспечить VM настроенный объём. Поэтому RAM виртуальной машины обычно сильнее резервируется, чем лимит памяти контейнера.

### Диск виртуальной машины

VM обычно получает виртуальный диск, например файл:

```text
ubuntu.vdi
ubuntu.qcow2
```

Гостевая ОС считает его обычным диском.

<a id="containerization"></a>
## Контейнеризация

**Контейнеризация — запуск приложения как изолированного процесса или группы процессов внутри существующей операционной системы.**

```text
Linux host
├── контейнер app
├── контейнер PostgreSQL
└── контейнер Redis
```

Все контейнеры используют общее ядро хоста:

```text
app ─────────┐
postgres ────┼── Linux kernel хоста
redis ───────┘
```

Контейнер:

- не имеет собственного ядра;
- не эмулирует полноценный компьютер;
- запускается быстрее VM;
- обычно занимает меньше памяти и диска;
- использует CPU и RAM хоста напрямую через ядро;
- изолируется namespaces;
- ограничивается cgroups.

### Ресурсы контейнера

Без лимитов контейнер обычно может использовать почти все свободные ресурсы хоста.

```bash
docker run my-app
```

Лимиты задаются отдельно:

```bash
docker run --cpus=2 --memory=1g my-app
```

Лимит памяти не означает немедленное резервирование 1 ГБ.

```text
Лимит: 1 ГБ
Фактическое использование: 200 МБ
```

Физически занято примерно 200 МБ.

<a id="vm-vs-container"></a>
## Виртуальная машина и контейнер: сравнение

| Характеристика | Виртуальная машина | Контейнер |
|---|---|---|
| Что виртуализируется | Целый компьютер | Процессы |
| Собственная ОС | Да | Нет |
| Собственное ядро | Да | Нет |
| Изоляция | Обычно сильнее | Обычно слабее |
| Запуск | Медленнее | Быстрее |
| Размер | Часто гигабайты | Часто мегабайты |
| Расход RAM | Выше | Ниже |
| CPU | Через vCPU и гипервизор | Напрямую через ядро хоста |
| RAM | Обычно выделяется VM | Потребляется динамически до лимита |
| Можно запустить другую ОС | Да | Требуется совместимое ядро |
| Плотность размещения | Ниже | Выше |

Главная формула:

```text
VM = виртуализируем целый компьютер.

Контейнер = изолируем процессы внутри существующей ОС.
```

На практике контейнеры часто работают внутри виртуальных машин:

```text
Физический сервер
└── виртуальная машина Linux
    └── Docker или Kubernetes
        ├── контейнер app
        └── контейнер worker
```

<a id="docker-architecture"></a>
## Docker: общая архитектура

Docker — набор инструментов для:

- сборки образов;
- хранения образов;
- запуска контейнеров;
- управления сетью;
- управления volumes;
- взаимодействия с registry.

Основная цепочка:

```text
Исходный код
    ↓
Dockerfile
    ↓
docker build
    ↓
Docker image
    ↓
docker run
    ↓
Docker container
```

### Архитектурные уровни

```text
Docker Compose
      ↓
Docker CLI / Docker API
      ↓
Docker Engine, dockerd
      ↓
containerd
      ↓
runc
      ↓
namespaces + cgroups
      ↓
Linux kernel
      ↓
CPU, RAM, диск, сеть
```

### Docker CLI

Команды пользователя:

```bash
docker build
docker run
docker ps
docker logs
docker stop
```

CLI отправляет запросы Docker Engine.

### Docker Engine

`dockerd` управляет:

- контейнерами;
- образами;
- networks;
- volumes;
- сборками;
- registry.

### containerd

Низкоуровневый менеджер жизненного цикла контейнеров:

- скачивает и хранит образы;
- запускает контейнеры;
- останавливает контейнеры;
- управляет runtime.

### runc

Непосредственно создаёт контейнерный процесс:

- namespaces;
- cgroups;
- root filesystem;
- ограничения безопасности;
- основной процесс контейнера.

<a id="container-user-space"></a>
## Образ ОС в контейнере: Alpine, Ubuntu и ядро

Строка:

```dockerfile
FROM alpine:3.22
```

не означает, что Docker загружает полноценную операционную систему Alpine с отдельным ядром.

Linux-систему упрощённо можно разделить на две части:

```text
Linux-система
├── kernel — ядро
│   ├── управление процессами
│   ├── управление памятью
│   ├── сеть
│   ├── файловые системы
│   └── драйверы
│
└── user space
    ├── shell
    ├── системные библиотеки
    ├── утилиты
    ├── пакетный менеджер
    ├── конфигурационные файлы
    └── пользовательские приложения
```

### Виртуальная машина

Виртуальная машина содержит обе части:

```text
VM с Alpine
├── собственное ядро Linux
├── Alpine user space
└── приложение
```

При запуске VM происходит загрузка отдельной гостевой ОС и её ядра.

### Контейнер

Docker image с Alpine содержит в основном **user space**, но не запускает отдельное ядро:

```text
Контейнер
├── Alpine user space
├── приложение
└── использует ядро Docker-хоста
```

В образе Alpine могут находиться:

- `/bin/sh`;
- BusyBox-утилиты: `ls`, `cp`, `cat`;
- библиотека `musl libc`;
- пакетный менеджер `apk`;
- файлы `/etc`;
- системные библиотеки и сертификаты.

При запуске контейнера Docker:

```text
1. Берёт файловую систему image.
2. Создаёт namespaces.
3. Создаёт cgroup.
4. Настраивает root filesystem контейнера.
5. Запускает CMD или ENTRYPOINT как процесс.
6. Этот процесс использует ядро Docker-хоста.
```

Пример:

```dockerfile
FROM alpine:3.22

CMD ["sleep", "1000"]
```

После `docker run` основным процессом контейнера будет:

```text
Контейнер
└── PID 1: sleep 1000
```

Отдельная Alpine OS при этом не загружается.

### Почему `/etc/os-release` показывает Alpine

Команда:

```bash
cat /etc/os-release
```

читает файл из файловой системы image. Поэтому она может показать Alpine Linux.

Команда:

```bash
uname -a
```

показывает сведения о ядре хоста, потому что контейнер использует именно его.

```text
/etc/os-release → user space из image
uname -a        → ядро Docker-хоста
```

### Что означает `AS builder`

Строка:

```dockerfile
FROM golang:1.25-alpine AS builder
```

читается так:

> Создать этап сборки с именем `builder` на основе image, содержащего Alpine user space, Go-компилятор и инструменты Go.

`builder` — имя этапа сборки, а не отдельный тип контейнера или ОС.

Пример multi-stage build:

```dockerfile
FROM golang:1.25-alpine AS builder

WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o server ./cmd/server

FROM alpine:3.22

WORKDIR /app
COPY --from=builder /app/server ./server

CMD ["./server"]
```

Здесь используются два этапа.

Первый этап:

```text
builder
├── Alpine user space
├── Go-компилятор
├── исходный код
└── собранный бинарник server
```

Второй этап:

```text
финальный image
├── минимальный Alpine user space
└── бинарник server
```

Инструкция:

```dockerfile
COPY --from=builder /app/server ./server
```

копирует файл из файловой системы этапа `builder` в финальный image.

В финальный image не обязаны попадать:

- исходный код;
- Go-компилятор;
- кэш модулей;
- инструменты сборки;
- остальные файлы builder-этапа.

### Что происходит при `RUN`

Инструкция:

```dockerfile
RUN go build -o server ./cmd/server
```

выполняется во время сборки image.

Docker создаёт временное изолированное окружение для текущего слоя и запускает в нём процесс `go build`. Этот процесс использует ядро Docker-хоста.

```text
Файловая система builder-этапа
            ↓
процесс go build
            ↓
ядро Docker-хоста
            ↓
новый слой image
```

`RUN` выполняется при `docker build`.

`CMD` и `ENTRYPOINT` выполняются при `docker run`.

### Образ `scratch`

Для статически собранного Go-приложения финальный image может быть пустым:

```dockerfile
FROM golang:1.25-alpine AS builder

WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o server ./cmd/server

FROM scratch

COPY --from=builder /app/server /server

CMD ["/server"]
```

`scratch` — пустой базовый image. В нём нет:

- shell;
- Alpine или Ubuntu;
- пакетного менеджера;
- `ls`, `cat`, `curl`;
- стандартных системных библиотек.

Финальная файловая система содержит только добавленные файлы:

```text
/
└── server
```

Контейнер всё равно запускается:

```text
процесс /server
        ↓
ядро Linux Docker-хоста
```

Это показывает, что контейнеру не нужна полноценная гостевая ОС.

### Зачем использовать Alpine в финальном image

Приложению могут понадобиться файлы user space:

- CA-сертификаты для HTTPS;
- timezone data;
- динамические библиотеки;
- `libc`;
- shell для startup-скрипта;
- диагностические утилиты.

Например:

```dockerfile
FROM alpine:3.22

RUN apk add --no-cache ca-certificates tzdata

COPY --from=builder /app/server /server

CMD ["/server"]
```

### Совместимость с ядром

Linux-программа ожидает системные вызовы Linux, поэтому Linux-контейнеру нужно Linux-ядро.

На Linux:

```text
Linux host
└── Linux containers
```

В Docker Desktop на Windows:

```text
Windows
└── WSL 2 / Linux VM
    ├── Linux kernel
    └── Linux containers
```

Alpine-контейнер использует ядро Linux-среды внутри WSL 2 или VM, а не ядро Alpine из image.

### Главное различие

```text
Alpine Docker image
=
файлы и библиотеки Alpine user space
без собственного запущенного ядра
```

```text
Виртуальная машина с Alpine
=
Alpine user space
+ собственное ядро
+ загрузка гостевой ОС
+ системные процессы
```

Поэтому утверждения не противоречат друг другу:

```text
Контейнер — изолированный процесс или группа процессов.

Image Alpine — файловое окружение, в котором этот процесс работает.

Ядро — общее ядро Docker-хоста.
```

<a id="dockerfile"></a>
## Dockerfile

**Dockerfile — инструкция по сборке Docker image.**

Пример:

```dockerfile
FROM golang:1.25-alpine AS builder

WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 go build -o server ./cmd/server

FROM alpine:3.22

WORKDIR /app
COPY --from=builder /app/server ./server

EXPOSE 8080
CMD ["./server"]
```

Основные инструкции:

| Инструкция | Назначение |
|---|---|
| `FROM` | базовый образ |
| `WORKDIR` | рабочая директория |
| `COPY` | копирование файлов |
| `RUN` | команда во время сборки |
| `ENV` | переменная окружения |
| `EXPOSE` | документирует порт |
| `CMD` | команда запуска по умолчанию |
| `ENTRYPOINT` | основная исполняемая команда |

### Multi-stage build

В первом этапе приложение компилируется, во второй переносится только готовый бинарник.

Преимущества:

- меньший финальный образ;
- нет компилятора и исходников;
- меньше поверхность атаки;
- быстрее скачивание.

<a id="docker-image"></a>
## Docker image и слои образа

**Docker image — неизменяемый шаблон файловой системы и конфигурации для запуска контейнеров.**

Он содержит:

- файлы приложения;
- библиотеки;
- системные зависимости;
- рабочую директорию;
- переменные окружения;
- команду запуска;
- метаданные.

```bash
docker build -t report-service:1.0 .
```

### Слои образа

Образ состоит из неизменяемых слоёв.

```dockerfile
FROM alpine
RUN apk add curl
COPY server /app/server
```

Логически:

```text
Слой 3: /app/server
Слой 2: установлен curl
Слой 1: Alpine Linux
```

Каждый слой хранит изменения относительно предыдущего.

Преимущества слоёв:

- переиспользование общих базовых слоёв;
- кэширование сборки;
- экономия диска;
- быстрая передача образов.

### Кэширование

Хороший порядок для Go:

```dockerfile
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN go build -o app
```

Пока `go.mod` и `go.sum` не изменились, Docker может не скачивать зависимости заново.

### Image tag

```text
report-service:1.0
report-service:1.1
report-service:latest
```

`latest` — обычное имя тега, а не автоматическая гарантия самой новой версии.

<a id="docker-container"></a>
## Docker container

**Контейнер — запущенный экземпляр Docker image.**

```text
Image → Container
```

Один образ может породить несколько контейнеров:

```text
report-service:1.0
├── report-1
├── report-2
└── report-3
```

### Writable layer

Слои образа неизменяемы. При запуске Docker добавляет сверху записываемый слой:

```text
Writable layer контейнера
─────────────────────────
Слой приложения
Слой зависимостей
Базовый слой
```

Изменения внутри контейнера попадают в writable layer.

Если контейнер удалить, writable layer тоже исчезнет.

Поэтому постоянные данные нельзя надёжно хранить только внутри файловой системы контейнера.

### Контейнер и процесс

Контейнер обычно живёт, пока работает его основной процесс.

```text
Контейнер
└── PID 1: ./server
```

Если основной процесс завершился, контейнер останавливается.

<a id="docker-volumes"></a>
## Docker volumes

**Volume — хранилище данных, существующее отдельно от жизненного цикла контейнера.**

```text
Контейнер PostgreSQL
        │
        │ /var/lib/postgresql/data
        ↓
Docker volume
        ↓
Диск хоста
```

Пример:

```bash
docker run \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16
```

Контейнер можно удалить и создать заново, а данные в volume останутся.

### Named volume

```bash
-v postgres-data:/var/lib/postgresql/data
```

Docker сам управляет расположением данных.

Подходит для:

- PostgreSQL;
- Redis persistence;
- RabbitMQ;
- Grafana;
- других постоянных данных.

### Bind mount

```bash
-v ./config.yaml:/app/config.yaml
```

Файл или директория хоста напрямую подключается внутрь контейнера.

```text
./config.yaml на хосте
        ↓
/app/config.yaml в контейнере
```

Подходит для:

- исходного кода при разработке;
- конфигурации;
- миграций;
- сертификатов.

### tmpfs

Данные хранятся в RAM и исчезают после остановки контейнера.

```bash
docker run --tmpfs /tmp my-app
```

### Разница

```text
Writable layer → временные данные конкретного контейнера.

Volume → постоянные данные, независимые от контейнера.

Bind mount → конкретный путь хоста подключён внутрь контейнера.
```

<a id="docker-networking"></a>
## Docker networking

У контейнера обычно есть отдельный network namespace:

- собственные интерфейсы;
- собственный IP;
- собственные порты;
- собственная таблица маршрутизации;
- собственный `localhost`.

### Главное правило localhost

Внутри контейнера:

```text
localhost = этот же контейнер
```

Допустим:

```text
Хост
├── контейнер app
└── контейнер postgres
```

Внутри `app`:

```text
localhost:5432
```

означает порт 5432 самого контейнера `app`, а не PostgreSQL.

Для подключения к PostgreSQL используют имя контейнера или Compose-сервиса:

```text
postgres:5432
```

### Bridge network

На одном хосте контейнеры обычно связываются через виртуальный bridge:

```text
Контейнер app
    │
Docker bridge
    │
Контейнер postgres
```

Docker предоставляет внутренний DNS, поэтому контейнеры можно находить по именам.

### Публикация портов

```bash
docker run -p 9000:8080 my-app
```

Формат:

```text
HOST_PORT:CONTAINER_PORT
```

То есть:

```text
localhost:9000 на хосте
        ↓
порт 8080 контейнера
```

В Compose:

```yaml
ports:
  - "9000:8080"
```

### EXPOSE

```dockerfile
EXPOSE 8080
```

`EXPOSE` не публикует порт на хосте. Это описание ожидаемого порта контейнера.

Реальная публикация выполняется через `-p` или `ports`.

### Основные типы Docker network

| Тип | Назначение |
|---|---|
| `bridge` | контейнеры на одном хосте |
| `host` | контейнер использует сеть хоста |
| `none` | сеть отключена |
| `overlay` | сеть между несколькими Docker-хостами |

<a id="docker-compose"></a>
## Docker Compose

**Docker Compose — способ декларативно описать и запустить систему из нескольких контейнеров.**

Пример:

```yaml
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://postgres:secret@postgres:5432/app
      REDIS_ADDR: redis:6379
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - postgres-data:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine

volumes:
  postgres-data:
```

Запуск:

```bash
docker compose up
```

В фоне:

```bash
docker compose up -d
```

Пересобрать образы:

```bash
docker compose up --build
```

Остановить и удалить контейнеры и сеть проекта:

```bash
docker compose down
```

Удалить также volumes:

```bash
docker compose down -v
```

`-v` удаляет постоянные данные Compose-проекта.

### Что делает Compose

```text
1. Читает compose.yaml.
2. Собирает или скачивает образы.
3. Создаёт сеть проекта.
4. Создаёт volumes.
5. Создаёт контейнеры.
6. Подключает их к сети.
7. Запускает основные процессы.
8. Публикует указанные порты.
```

Сервисы одной Compose-сети обращаются друг к другу по имени:

```text
app → postgres:5432
app → redis:6379
```

### depends_on

`depends_on` задаёт порядок запуска контейнеров, но не гарантирует готовность приложения внутри контейнера.

```text
Контейнер PostgreSQL запущен
≠
PostgreSQL уже готов принимать запросы
```

Для проверки готовности используют `healthcheck`, а клиент должен уметь повторять подключение.

<a id="summary-model"></a>
## Итоговая модель

### Процесс и поток

```text
Процесс
├── изолированная виртуальная память
├── общий heap
├── общие файлы и сокеты
│
├── поток 1
│   └── собственный stack
│
└── поток 2
    └── собственный stack
```

### Виртуальная машина

```text
Приложение
    ↓
Guest OS и собственное ядро
    ↓
виртуальные CPU, RAM и диск
    ↓
гипервизор
    ↓
физические ресурсы
```

### Контейнер

```text
Приложение как процесс
    ↓
namespaces: что видно
cgroups: сколько ресурсов доступно
    ↓
общее ядро хоста
    ↓
физические CPU, RAM, диск и сеть
```

### Docker

```text
Dockerfile
    ↓ docker build
Image
    ↓ docker run
Container
```

```text
Image
= неизменяемый шаблон и слои файловой системы

Alpine/Ubuntu в image
= user space: библиотеки, shell, утилиты и файлы
  без отдельного ядра

Container
= запущенный процесс или группа процессов,
  использующие ядро Docker-хоста

AS builder
= имя промежуточного этапа сборки

Multi-stage build
= сборка приложения в одном этапе
  и перенос только нужных файлов в финальный image

Writable layer
= временные изменения контейнера

Volume
= постоянные данные вне жизненного цикла контейнера

Network
= связь контейнеров и публикация портов

Compose
= декларативное описание нескольких сервисов
```

### Самые важные формулировки

```text
Процесс — изолированное окружение запущенной программы.

Поток — последовательность выполнения внутри процесса.

Потоки одного процесса разделяют heap, код, файлы и сокеты,
но у каждого свой stack и состояние выполнения.

VM виртуализирует целый компьютер с собственной ОС и ядром.

Контейнер изолирует процессы внутри существующей ОС
и использует общее ядро хоста.

Namespace ограничивает видимость.

Cgroup ограничивает ресурсы.

Image — неизменяемый шаблон.

Container — запущенный экземпляр image.

Volume хранит постоянные данные отдельно от контейнера.

Docker network позволяет контейнерам общаться по именам.

Docker Compose описывает и запускает систему из нескольких контейнеров.

Alpine или Ubuntu в Docker image — это в основном user space,
а не отдельная загружаемая ОС с собственным ядром.

Контейнерный процесс выполняет системные вызовы через ядро Docker-хоста.

`AS builder` задаёт имя этапа сборки,
из которого можно копировать результаты в финальный image.
```
