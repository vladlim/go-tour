## 1. Общая картина: что делает ОС

Операционная система — это прослойка между программами и железом.

Программа хочет:

- читать файлы;
- писать в stdout;
- открывать TCP-соединения;
- принимать входящие запросы;
- выделять память;
- запускать другие процессы;
- работать с таймерами;
- получать сигналы.

Но обычная программа не должна напрямую управлять диском, сетевой картой, памятью и процессором. Иначе любая ошибка в приложении могла бы сломать всю систему.

Поэтому ОС дает приложениям безопасный API через системные вызовы.

Упрощенно:

```text
Приложение
  ↓
Стандартная библиотека / runtime
  ↓
Системный вызов
  ↓
Ядро ОС
  ↓
Железо / файловая система / сеть / память
```

## 2. User Space и Kernel Space

### 2.1. Что такое User Space

**User Space** — это режим, в котором работают обычные пользовательские программы.

Например:

- твой Go-сервис;
- браузер;
- PostgreSQL;
- Redis;
- nginx;
- bash;
- docker client.

В User Space программа не имеет прямого доступа к железу и критическим структурам ОС.

Она не может напрямую:

- читать произвольную физическую память;
- управлять сетевой картой;
- писать напрямую на диск;
- менять таблицы страниц;
- отключать прерывания;
- управлять другими процессами без разрешения ОС.

Программа видит не физическую память, а свое **виртуальное адресное пространство**.

---

### 2.2. Что такое Kernel Space

**Kernel Space** — это привилегированный режим, в котором работает ядро операционной системы.

Ядро умеет:

- планировать процессы и потоки;
- управлять памятью;
- работать с файловыми системами;
- работать с сетью;
- управлять устройствами через драйверы;
- обрабатывать системные вызовы;
- контролировать права доступа.

Kernel Space имеет доступ к критическим ресурсам системы.

---

### 2.3. Зачем нужно разделение

Разделение нужно для безопасности и стабильности.

Если обычная программа падает, она не должна уронить всю систему.

Если программа хочет прочитать файл, она не лезет напрямую на диск. Она просит ОС:

```text
ОС, открой мне файл /tmp/a.txt на чтение.
```

Ядро проверяет:

- существует ли файл;
- есть ли права;
- не занят ли ресурс;
- можно ли выполнить операцию.

И только потом возвращает результат.

---

### 2.4. Переключение User Space → Kernel Space

Когда программа делает системный вызов, происходит переход из User Space в Kernel Space.

Упрощенно:

```text
1. Программа вызывает функцию, например os.ReadFile.
2. Стандартная библиотека подготавливает syscall.
3. CPU переходит в привилегированный режим.
4. Ядро выполняет операцию.
5. Ядро возвращает результат.
6. CPU возвращается в пользовательский режим.
```

Важно: иногда это называют context switch, но точнее различать:

- **mode switch** — переход user mode ↔ kernel mode внутри выполнения;
- **context switch** — переключение CPU с одного потока/процесса на другой.

Системный вызов обязательно требует перехода в kernel mode, но не всегда означает переключение на другой процесс.

## 3. Системные вызовы syscall

### 3.1. Что такое syscall

**Syscall** — это системный вызов, то есть запрос программы к ядру ОС выполнить привилегированную операцию.

Примеры операций:

- открыть файл;
- прочитать файл;
- записать данные в stdout;
- создать сокет;
- подключиться к серверу;
- принять TCP-соединение;
- выделить память;
- создать процесс;
- завершить процесс.

В Go мы редко вызываем syscall напрямую. Обычно мы используем высокоуровневые пакеты:

```go
os.Open(...)
os.ReadFile(...)
net.Listen(...)
http.ListenAndServe(...)
exec.Command(...)
```

А внутри они используют системные вызовы ОС.

---

### 3.2. Примеры syscall на Linux

Типичные системные вызовы:

```text
open/openat  — открыть файл
read         — прочитать из файла/сокета
write        — записать в файл/сокет/stdout
close        — закрыть дескриптор
socket       — создать сокет
connect      — подключиться к удаленному адресу
accept       — принять входящее соединение
bind         — привязать сокет к адресу
listen       — начать слушать порт
mmap         — отобразить память
fork/clone   — создать процесс/поток
execve       — заменить текущий процесс другой программой
epoll_wait   — ждать события на файловых дескрипторах
```

---

### 3.3. Пример: чтение файла

Go-код:

```go
data, err := os.ReadFile("test.txt")
```

Упрощенно под капотом:

```text
open("test.txt")
read(fd, buffer)
close(fd)
```

То есть `os.ReadFile` — удобная обертка, но реальную работу с файлом делает ядро ОС.

---

### 3.4. Пример: HTTP-запрос

Go-код:

```go
resp, err := http.Get("https://example.com")
```

Под капотом может быть много операций:

```text
DNS lookup
socket
connect
TLS handshake
write HTTP request
read HTTP response
close socket
```

С точки зрения Go это один вызов, но на уровне ОС это набор системных вызовов.

---

### 3.5. Почему syscall дороже обычной функции

Обычная функция вызывается внутри User Space.

Syscall требует перехода:

```text
User Space → Kernel Space → User Space
```

Ядро должно:

- проверить права;
- проверить аргументы;
- проверить указатели и буферы;
- выполнить операцию;
- возможно скопировать данные между kernel memory и user memory;
- вернуть результат или ошибку.

Поэтому системные вызовы дороже обычных вызовов функций.

Из-за этого, например, читать файл по одному байту неэффективно:

```go
buf := make([]byte, 1)
for {
    _, err := f.Read(buf)
    ...
}
```

Лучше читать буферами или использовать `bufio.Reader`.

---

### 3.6. Что такое epoll

`epoll` — механизм Linux для эффективного ожидания событий на большом количестве файловых дескрипторов.

Например, у сервера 10 000 TCP-соединений. Неэффективно постоянно опрашивать каждое соединение вручную.

Лучше сказать ядру:

```text
Разбуди меня, когда на каком-то из этих сокетов появятся данные.
```

Для этого и используется `epoll`.

Основные идеи:

```text
epoll_create — создать epoll instance
epoll_ctl    — добавить fd в наблюдение
epoll_wait   — ждать события
```

Go runtime использует похожий механизм в netpoller, чтобы эффективно парковать goroutine, ожидающие сеть.

## 4. Файловые дескрипторы

### 4.1. Что такое файловый дескриптор

**Файловый дескриптор** — это число, которое ОС выдает процессу как идентификатор открытого ресурса.

Ресурсом может быть:

- обычный файл;
- директория;
- TCP-сокет;
- Unix-сокет;
- pipe;
- terminal;
- device;
- stdin/stdout/stderr.

Пример:

```text
0 — stdin
1 — stdout
2 — stderr
3 — открытый файл
4 — TCP-сокет
5 — pipe
```

Когда ты пишешь:

```go
f, err := os.Open("data.txt")
```

ОС открывает файл и возвращает файловый дескриптор. Go заворачивает его в `*os.File`.

---

### 4.2. stdin, stdout, stderr

У каждого обычного процесса по умолчанию есть три стандартных дескриптора:

```text
0 — stdin  — стандартный ввод
1 — stdout — стандартный вывод
2 — stderr — стандартный поток ошибок
```

Например:

```go
fmt.Println("hello")
```

в итоге пишет в stdout, то есть в fd `1`.

А ошибки CLI-программы лучше писать в stderr:

```go
fmt.Fprintln(os.Stderr, "error:", err)
```

---

### 4.3. Почему fd нужно закрывать

Если открыть файл или соединение и не закрыть его, процесс продолжит держать файловый дескриптор.

Пример:

```go
resp, err := http.Get(url)
if err != nil {
    return err
}
defer resp.Body.Close()
```

Если не закрывать `resp.Body`, можно получить утечку соединений и ошибку:

```text
too many open files
```

У процесса есть лимит на количество открытых fd.

Проверить лимиты можно так:

```bash
ulimit -n
cat /proc/<pid>/limits
```

Посмотреть открытые fd процесса:

```bash
ls /proc/<pid>/fd
lsof -p <pid>
```

---

### 4.4. Почему удаленный файл может продолжать занимать место

На Linux файл реально освобождает место на диске только когда выполнены два условия:

```text
1. файл удален из директории;
2. больше ни один процесс не держит его открытым.
```

Если процесс открыл большой лог-файл, а потом файл удалили через `rm`, место может не освободиться.

Почему?

Потому что процесс всё еще держит открытый fd на этот файл.

Диагностика:

```bash
lsof | grep deleted
lsof +L1
```

Решение:

- заставить процесс закрыть дескриптор;
- перезапустить процесс;
- настроить корректную log rotation;
- в крайнем случае очистить файл через `/proc/<pid>/fd/<fd>`, если понимаешь последствия.

## 5. Процесс и поток

### 5.1. Что такое процесс

**Процесс** — это экземпляр запущенной программы.

У процесса есть свои ресурсы:

- виртуальное адресное пространство;
- таблица файловых дескрипторов;
- переменные окружения;
- права пользователя;
- текущая директория;
- PID;
- обработчики сигналов;
- один или несколько потоков.

Процессы изолированы друг от друга. Один процесс не может просто так читать память другого процесса.

Для обмена данными между процессами нужны специальные механизмы IPC:

- pipes;
- sockets;
- signals;
- shared memory;
- files;
- message queues.

---

### 5.2. Что такое поток

**Поток** — это поток выполнения внутри процесса.

У потока есть:

- свой stack;
- свои регистры CPU;
- свой instruction pointer;
- свое состояние выполнения.

Но потоки одного процесса обычно разделяют:

- heap;
- глобальные переменные;
- файловые дескрипторы;
- адресное пространство процесса.

Поэтому потоки могут легко обмениваться данными через общую память, но из-за этого возникают гонки данных.

---

### 5.3. Процесс vs поток коротко

```text
Процесс:
  отдельное адресное пространство
  свои ресурсы ОС
  тяжелее создавать
  изолирован от других процессов

Поток:
  живет внутри процесса
  разделяет память процесса
  легче процесса
  требует синхронизации при доступе к общей памяти
```

---

### 5.4. Linux: task, process, thread

В Linux процессы и потоки представлены похожими структурами ядра. На низком уровне это task.

Разница в том, какие ресурсы разделяются.

Если новый task разделяет адресное пространство, таблицу fd и другие ресурсы с родителем — это поток.

Если у него отдельное адресное пространство — это отдельный процесс.

Грубо:

```text
процесс и поток в Linux — оба task,
но потоки разделяют больше структур,
а процессы изолированы сильнее.
```

---

### 5.5. Чем goroutine отличается от OS thread

Goroutine — это не поток ОС.

Goroutine — легковесная сущность Go runtime.

Go runtime сам распределяет много goroutine по меньшему количеству OS threads.

Модель Go часто описывают как GMP:

```text
G — goroutine
M — machine, OS thread
P — processor, контекст выполнения Go-кода
```

Когда goroutine ждет сеть, runtime может припарковать ее и дать OS thread выполнять другие goroutine.

## 6. Виртуальная память, физическая память и swap

### 6.1. Что такое виртуальная память

Каждый процесс видит свое виртуальное адресное пространство.

Процессу кажется, что у него есть непрерывная память:

```text
0x0000...
0x1000...
0x2000...
...
```

Но реально эти виртуальные адреса отображаются на физическую память через таблицы страниц.

Этим управляет ОС и MMU процессора.

---

### 6.2. Зачем нужна виртуальная память

Виртуальная память нужна для:

- изоляции процессов;
- защиты памяти;
- lazy allocation;
- memory mapping файлов;
- shared libraries;
- copy-on-write;
- swap;
- удобного управления памятью.

Благодаря виртуальной памяти один процесс не может просто так испортить память другого процесса.

---

### 6.3. Физическая память

Физическая память — это реальная RAM.

Но процесс обычно не работает с физическими адресами напрямую. Он работает с виртуальными адресами.

ОС решает, какие виртуальные страницы реально находятся в RAM, какие можно выгрузить, какие еще не выделены физически.

---

### 6.4. Swap

Swap — это область на диске, которую ОС может использовать как продолжение памяти.

Если RAM не хватает, часть редко используемых страниц может быть выгружена в swap.

Плюс:

```text
система может пережить нехватку RAM дольше
```

Минус:

```text
диск намного медленнее RAM, поэтому при активном swap система сильно тормозит
```

Проверить память и swap:

```bash
free -h
vmstat 1
```

## 7. Утечка памяти и OOM Killer

### 7.1. Что такое утечка памяти

Утечка памяти — это ситуация, когда программа продолжает удерживать память, которая ей уже не нужна.

В Go есть GC, но утечки всё равно возможны.

GC освобождает только недостижимые объекты. Если объект всё еще достижим по ссылке, GC считает его нужным.

---

### 7.2. Примеры утечек в Go

Типичные причины:

#### Бесконечно растущий map/cache

```go
cache[key] = value
```

Если нет TTL/eviction, cache может расти бесконечно.

#### Слайс удерживает большой underlying array

```go
small := big[:10]
```

`small` маленький по len, но может удерживать весь большой массив.

#### Goroutine leak

Goroutine зависла на чтении из канала или ожидании и никогда не завершается.

#### Не закрыли response body

```go
resp, _ := http.Get(url)
// забыли resp.Body.Close()
```

Это может привести к утечке соединений и fd.

#### Таймеры/тикеры

```go
ticker := time.NewTicker(time.Second)
// забыли ticker.Stop()
```

---

### 7.3. Что будет, когда память закончится

Зависит от ОС, настроек, swap и container limit.

Если памяти становится мало, система может:

- начать активно использовать swap;
- начать сильно тормозить;
- отказать в выделении памяти;
- запустить OOM Killer;
- убить один или несколько процессов.

---

### 7.4. Что такое OOM Killer

OOM Killer — механизм Linux, который выбирает процесс для убийства, когда системе не хватает памяти.

OOM = Out Of Memory.

Если ядро не может удовлетворить запросы на память, оно выбирает процесс-жертву и завершает его.

Обычно выбор зависит от:

- сколько памяти потребляет процесс;
- `oom_score`;
- `oom_score_adj`;
- настроек cgroup/container;
- важности процесса с точки зрения системы.

Посмотреть score:

```bash
cat /proc/<pid>/oom_score
cat /proc/<pid>/oom_score_adj
```

---

### 7.5. Swap включен или выключен

Если swap включен:

```text
система может долго жить в состоянии нехватки RAM,
но начинает сильно тормозить из-за постоянного обмена страницами с диском.
```

Если swap выключен:

```text
при нехватке памяти OOM Killer может быстрее убить процесс.
```

Важно: OOM Killer не обязан убить именно твой сервис. Он выбирает жертву по своей эвристике и настройкам.

---

### 7.6. Container memory limit

Если сервис работает в Docker/Kubernetes, есть еще лимит cgroup.

Например контейнеру дали 512 MB.

Даже если на сервере свободно 20 GB RAM, процесс внутри контейнера может быть убит при превышении лимита контейнера.

В Kubernetes это часто выглядит как:

```text
OOMKilled
```

## 8. Как это связано с Go

### 8.1. Go runtime и ОС

Go-программа работает в User Space, но Go runtime активно взаимодействует с ОС.

Runtime занимается:

- планированием goroutine;
- управлением OS threads;
- GC;
- выделением памяти;
- обработкой таймеров;
- netpoller;
- panic/defer/recover;
- stack growth goroutine.

---

### 8.2. Сеть в Go

Когда goroutine ждет данные из сети, Go runtime может не блокировать весь OS thread.

Упрощенно:

```text
goroutine хочет читать из сокета
  ↓
данных нет
  ↓
runtime паркует goroutine
  ↓
fd регистрируется в netpoller/epoll
  ↓
OS thread выполняет другие goroutine
  ↓
приходят данные
  ↓
epoll будит runtime
  ↓
goroutine продолжает работу
```

---

### 8.3. Файлы в Go

Файловые операции тоже идут через ОС.

Например:

```go
os.Open(...)
f.Read(...)
f.Close()
```

Внутри это системные вызовы.

Важно закрывать файлы:

```go
f, err := os.Open("data.txt")
if err != nil {
    return err
}
defer f.Close()
```

<a id="answers"></a>

## 10. Ответы на задания

<a id="answer-user-kernel"></a>

### 10.1. Что такое User Space и Kernel Space? Зачем нужно такое разделение?

Короткий ответ:

> User Space — это режим, в котором работают обычные приложения. Kernel Space — это привилегированный режим, в котором работает ядро ОС. Разделение нужно для безопасности и стабильности: обычная программа не может напрямую управлять железом, памятью и другими процессами. Для операций с файлами, сетью и памятью программа обращается к ядру через системные вызовы.

Расширенный ответ:

> Приложение работает в user mode и видит свое виртуальное адресное пространство. Когда ему нужно прочитать файл, открыть сокет или выделить память у ОС, оно делает syscall. CPU переходит в kernel mode, ядро проверяет права и выполняет операцию. Это защищает систему: падение или ошибка пользовательской программы не должны ломать ядро и другие процессы.

---

<a id="answer-syscall"></a>

### 10.2. Что такое syscall?

Короткий ответ:

> Syscall — это системный вызов, то есть способ, которым программа просит ядро ОС выполнить привилегированную операцию: прочитать файл, записать данные, открыть сокет, создать процесс и так далее.

Расширенный ответ:

> Например `os.ReadFile` в Go внутри приводит к системным вызовам вроде `open`, `read`, `close`. При syscall происходит переход из user space в kernel space. Программа передает ядру номер вызова и аргументы, ядро выполняет операцию и возвращает результат или ошибку. Для ожидания событий на множестве fd Linux использует `epoll`, а Go runtime использует netpoller поверх подобных механизмов.

---

<a id="answer-fd"></a>

### 10.3. Что такое файловый дескриптор?

Короткий ответ:

> Файловый дескриптор — это числовой идентификатор открытого ресурса внутри процесса. Через него процесс работает с файлами, сокетами, pipe, stdin, stdout и stderr.

Расширенный ответ:

> Когда программа открывает файл, ОС возвращает ей fd. Например `0` — stdin, `1` — stdout, `2` — stderr. Последующие операции чтения/записи идут через этот fd. Важно закрывать дескрипторы, иначе можно получить утечку fd и ошибку `too many open files`.

Дополнительный вопрос:

> Что будет, если удалить большой файл, но место не освободилось?

Ответ:

> Скорее всего файл все еще открыт каким-то процессом. В Linux удаление имени файла из директории не освобождает место, пока последний файловый дескриптор на этот файл не будет закрыт. Нужно найти процесс через `lsof +L1` или `lsof | grep deleted` и заставить его закрыть fd, обычно перезапуском или корректной log rotation.

---

<a id="answer-memory-leak"></a>

### 10.4. Утечка памяти: что будет, когда память закончится?

Короткий ответ:

> Если память заканчивается, система может начать использовать swap, сильно тормозить, отказать в выделении памяти или запустить OOM Killer, который убьет один из процессов.

Расширенный ответ:

> Если swap включен, система может некоторое время продолжать работать, но очень медленно, потому что страницы памяти будут выгружаться на диск. Если swap выключен или лимит контейнера исчерпан, OOM Killer может убить процесс. Он не обязан убить именно наш сервис; выбор зависит от `oom_score`, потребления памяти, cgroup и настроек `oom_score_adj`.

Дополнительный вопрос:

> На какой тип памяти опирается система при OOM?

Ответ:

> ОС управляет виртуальной памятью, но реальное давление возникает из-за нехватки физических страниц RAM и swap/commit limit. В контейнерах важен еще cgroup memory limit. OOM Killer выбирает жертву по метрикам процесса и настройкам, а не просто по одному числу `virtual memory`.

<a id="answer-process-thread"></a>

### 10.5. Чем отличается процесс от системного потока?

Короткий ответ:

> Процесс — это экземпляр запущенной программы с собственным адресным пространством и ресурсами. Поток — это поток выполнения внутри процесса. Потоки одного процесса разделяют память и файловые дескрипторы, но имеют свой stack и регистры.

Расширенный ответ:

> Процессы изолированы друг от друга и обычно не шарят память напрямую. Для общения между процессами нужны IPC-механизмы: сокеты, pipe, сигналы, shared memory, файлы. Потоки внутри одного процесса разделяют heap и глобальные данные, поэтому могут обмениваться информацией через общую память, но нужно использовать синхронизацию, чтобы не получить гонки данных.

Дополнительный вопрос:

> Как процессы могут обмениваться информацией?

Ответ:

> Через sockets, pipes, signals, shared memory, files, message queues. В Go-сервисах чаще всего это сеть: HTTP/gRPC, TCP, Unix sockets, либо брокеры сообщений.
