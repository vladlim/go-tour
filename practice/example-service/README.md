# example-service

Учебный HTTP-сервис на Go и PostgreSQL. Команды выполняются из этой директории.
Нужны Go >= 1.25.3, Docker Compose и make. В WSL должна быть включена интеграция Docker Desktop.
Если Go установлен в `/usr/local/go`, но команда не найдена, добавь его в PATH:
`export PATH="/usr/local/go/bin:$PATH"`.

## Запуск

```sh
make migrate-up
make run
curl -i http://localhost:8080/ping
```

`migrate-up` поднимает PostgreSQL, ждёт готовности и применяет миграции через golang-migrate.
Повторный запуск не дублирует данные: версия хранится в служебной таблице `schema_migrations`.
Миграции запускаются отдельно от HTTP-сервера.

Локальная БД: `localhost:5432`, база `example_service`, пользователь `app`, пароль `app_local`.
Внутри Compose адрес БД — `db:5432`. На хосте порт 5432 должен быть свободен.
Параметры приложения находятся в `configs/config.yaml`; другой файл: `go run ./cmd -config_path ./configs/config.yaml`.
`DB_PASSWORD` переопределяет пароль приложения; при изменении учётных данных нужно согласовать настройки БД и мигратора в Compose.
Эти учётные данные предназначены для локальной учебной среды.

```sh
make psql             # SQL-консоль
make check            # сборка пакетов и go vet
make db-down          # остановка; данные сохраняются в Docker volume
```

Ctrl+C останавливает приём новых HTTP-запросов, даёт активным до 10 секунд на завершение,
затем закрывает пул БД. При превышении таймаута HTTP-соединения закрываются принудительно.

## Таблицы

- `users`: имя, уникальный email, дата создания. 10 004 пользователя.
- `projects`: название, описание, владелец (`users`). 2 003 проекта.
- `tasks`: проект, необязательный исполнитель, заголовок, описание, статус, приоритет, срок. 1 000 007 задач.

Связи: `users → projects` (владелец), `projects → tasks`, `users → tasks` (исполнитель).
Статусы: `todo`, `in_progress`, `done`. Приоритет: 1 — низкий, 2 — средний, 3 — высокий.
Даты хранятся как `timestamptz`; срок и исполнитель могут быть NULL.
Удаление проекта каскадно удаляет задачи. Удаление исполнителя сбрасывает `assignee_id` в NULL.
Удалить владельца существующего проекта нельзя, пока проект не удалён или не передан другому владельцу.
После всех миграций остаются только индексы PRIMARY KEY и UNIQUE(email).
Индексы внешних ключей из первой миграции удаляются в третьей, чтобы создавать их самостоятельно.

`000001` создаёт схему, `000002` добавляет маленький понятный набор, `000003` — большой набор для индексов.
Третья миграция применяется и к уже поднятой базе командой `make migrate-up`.
Генерация миллиона задач может занять некоторое время и несколько сотен МБ диска.
ID генерируются автоматически;
при добавлении новых строк передавать ID не нужно. Каждый SQL-файл обёрнут в транзакцию.

```sql
SELECT t.id, t.title, t.status, p.name AS project, u.name AS assignee
FROM tasks t
JOIN projects p ON p.id = t.project_id
LEFT JOIN users u ON u.id = t.assignee_id
ORDER BY t.id;
```

Down-миграций нет: база поднимается для дальнейших ручных экспериментов.
При изменении схемы добавляй новую миграцию, а не редактируй уже применённую.

## Эксперименты с индексами

Большой набор воспроизводимый: примерно 80% задач завершены, 15% ожидают выполнения,
5% в работе. 20% без исполнителя, 25% без срока. Часть проектов и пользователей без задач.
Даты создания распределены на два года. После загрузки выполняется ANALYZE.

Сначала посмотри план без индекса:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title, created_at
FROM tasks
WHERE project_id = 4 AND status = 'todo'
ORDER BY created_at DESC
LIMIT 20;
```

Возьми существующий project_id из `SELECT id FROM projects ORDER BY id LIMIT 10`.
Создай индекс и сравни план того же запроса:

```sql
CREATE INDEX tasks_project_status_created_idx
ON tasks (project_id, status, created_at DESC);
```

Смотри тип сканирования, количество прочитанных буферов, наличие Sort и время выполнения.
Повтори запросы несколько раз: первый запуск может читать с диска, последующие — из кеша.
Для сравнения на одном состоянии кеша можно создать индекс, прогреть запрос, удалить индекс
и снова выполнить запрос несколько раз. Само наличие индекса не гарантирует его использование.
Другие упражнения: индекс по исполнителю, частичный индекс для незавершённых задач,
сравнение выборки всех `done` и редких `in_progress`, фильтрация по диапазону дат.

## Что тренировать

1. `GET /tasks`: список с фильтрами по проекту, исполнителю, статусу; limit/offset и сортировка.
2. `GET /tasks/{id}`: одна задача с именем исполнителя; различать 404 и ошибку БД.
3. `POST /tasks`: создание с проверкой полей и обработкой нарушения внешнего ключа.
4. `PATCH /tasks/{id}`: изменение статуса и назначение/снятие исполнителя.
5. `GET /projects`: число задач и завершённых задач, включая проекты без задач (LEFT JOIN).
6. `POST /projects`: проект и первая задача в одной транзакции.

Путь запроса: `middleware → handler → service → storage → pgxpool → PostgreSQL`.
HTTP/JSON остаётся в handler, правила — в service, SQL — в storage.
Пустые интерфейсы `Service` и `storage` пока заглушки: добавляй в них методы по мере реализации ручек.
Передавай `r.Context()` через эти слои в запросы БД; значения SQL передавай через `$1`, `$2`.
Recovery логирует панику со стеком, но не откатывает изменения и не заменяет уже отправленный HTTP-статус.
